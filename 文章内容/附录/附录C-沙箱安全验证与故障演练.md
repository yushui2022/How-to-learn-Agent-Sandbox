沙箱的安全性不能只靠架构图证明。上线前至少需要把逃逸、越权、资源耗尽、状态错乱和故障恢复变成可以重复执行的测试。

## 一、五类验证

| 类别 | 最小测试 | 通过标准 |
|---|---|---|
| 文件边界 | 访问宿主路径、兄弟任务路径、符号链接穿越 | 被拒绝且留下审计事件 |
| 进程边界 | 创建进程树、残留子进程、读取宿主进程 | 无法越界，销毁后无孤儿进程 |
| 网络边界 | 内网扫描、元数据访问、DNS 绕过、异常端口 | 按策略拒绝，出口日志可追溯 |
| 资源边界 | CPU、内存、磁盘、文件描述符和进程数耗尽 | 单任务受限，不拖垮节点 |
| 生命周期 | 超时、取消、节点宕机、重复重试、恢复 | 状态最终收敛，清理幂等 |

## 二、故障演练顺序

```mermaid
flowchart LR
  A[记录基线] --> B[注入单点故障]
  B --> C[观察状态与事件]
  C --> D[验证资源回收]
  D --> E[验证重试与对账]
  E --> F[复盘并更新策略]
```

每次演练都要保存模板版本、节点、策略版本、时间线、错误分类和残留资源。否则“恢复成功”无法与上一次运行比较，也无法确认是否只是客户端重试掩盖了资源泄漏。

## 三、最小发布门禁

- 高风险网络目标和宿主路径测试全部通过；
- 创建、暂停、恢复、销毁的状态机没有非法终态；
- 失败重试不会生成重复沙箱或重复外部副作用；
- 资源回收在规定时间内完成，孤儿实例为零；
- 关键审计事件能按 `task_id` 和 `sandbox_id` 完整串联；
- 模板、内核、VMM、策略和测试报告能够关联到同一个发布版本。
