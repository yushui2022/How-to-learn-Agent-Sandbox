## 先看结论：四层平面各回答一个问题

把 CubeSandbox 想成四层叠加，而不是一堆服务：

~~~mermaid
mindmap
  root((CubeSandbox))
    继承平面
      KVM 硬件隔离
      Cloud Hypervisor / RustVMM
      virtio 最小设备集
      PVH 直启内核
      每 VM 独立 VMM 进程
      回答：墙怎么砌
    供给语义
      模板预热
      CubeCoW / FICLONE
      内存快照恢复
      vsock 控制通道
      Full / Incremental / SoftDirty
      pause / resume / rollback / clone
      回答：环境怎样快速出生和复用
    治理语义
      CubeVS eBPF
      CubeEgress L7 出口
      凭据按请求注入
      allow / deny 策略
      审计与租户配额
      回答：为什么企业敢让模型联网
    控制平面
      CubeAPI
      CubeMaster
      Redis 状态真相
      Template Store
      节点水位与调度
      回答：规模上来后谁决定去哪
~~~

> **读图提示：**这四层是分析框架，不等于四组独立进程或四个部署单元；同一个组件可以跨层承载不同语义，例如 CubeVS 同时承载转发和策略。

记住四个动词就够了：

- **继承平面负责“隔离”**：给每个沙箱一台独立内核的 MicroVM。
- **供给语义负责“复用”**：把“启动”改造成“从模板和快照恢复”。
- **治理语义负责“约束”**：让网络、凭据和审计可控、可追溯。
- **控制平面负责“编排”**：决定在哪个节点创建、状态以谁为准。

> **核心句：**继承让它够薄，供给让它够快，治理让它敢上生产，控制面让它能扩到大规模。

图中有三条边界：

- **控制平面**做调度、状态和模板选择，不亲自操作每台 VM。

## 一、继承平面：先有一台“快而薄的 VM”

CubeSandbox 的隔离底座不是从零发明的，它使用 Cloud Hypervisor / RustVMM 这一支 MicroVM 路线，并在本地 CubeHypervisor 中继续定制。Firecracker、Cloud Hypervisor 和 crosvm 之间更适合画成“共享 RustVMM 能力的并行路线”，不要画成单线继承。

~~~mermaid
flowchart LR
  crosvm["crosvm"] --> rust["rust-vmm 共享 crates"]
  fire["Firecracker"] --> rust
  ch["Cloud Hypervisor"] --> rust
  ch --> cube["CubeHypervisor<br/>CubeSandbox 的本地 fork / 定制"]
  rust --> cube
~~~

### 1. KVM 负责画出硬件墙

下面是 x86 的示意；ARM64 对应的是 EL2 和 stage-2 地址翻译。

~~~mermaid
flowchart LR
  gva["guest 虚拟地址"] --> gpa["GPA<br/>guest physical address"]
  gpa --> ept["EPT / NPT<br/>二级地址翻译"]
  ept --> hpa["HPA<br/>host physical address"]

  guest["guest 普通指令"] --> cpu["硬件直接执行"]
  sensitive["敏感操作"] --> exit["VM exit"]
  exit --> vmm["VMM / CubeHypervisor"]
  vmm --> cpu

  classDef boundary fill:#ffe8e8,stroke:#bf3b3b,color:#321;
  class exit,vmm boundary;
~~~

这层回答的是“**墙怎么砌**”。它提供硬件隔离边界，但还没有回答“怎样让 Agent 环境按需出生、保存和回滚”。

### 2. 三刀减法：设备、启动链、进程模型

~~~mermaid

  qemu["完整机型<br/>设备多·启动链长·兼容包袱重"]
  qemu --> d["削设备<br/>保留 virtio block/net/vsock、串口等最小集合"]
  d --> b["削启动链<br/>PVH 直载 Linux 内核，跳过固件与 bootloader"]

  classDef cut fill:#fff4dc,stroke:#c78a12,color:#321;

~~~

到这里还只是 VM，不是完整的 Agent 沙箱。如果每次创建都重新引导内核、初始化服务、复制磁盘，速度仍然会被启动链限制。真正突破“纯削薄路线”的，是下一层的供给语义。

## 二、供给语义：把“启动”换成“恢复”

供给语义不是再造一套虚拟化，而是把底座已有机制重新组合成四种复用：

~~~mermaid
flowchart LR
  mmap["内存映射 / KVM memslot"] --> restore["快照映射恢复<br/>少做引导"]
  reflink["本地 XFS/Btrfs reflink / FICLONE"] --> disk["磁盘派生<br/>少做拷贝"]
  vsock["virtio-vsock"] --> cmd["guest 控制通道<br/>Shim ↔ cube-agent"]
  dirty["pagemap / dirty log / soft-dirty"] --> inc["增量快照<br/>只处理本轮或累计变化"]

  restore --> fast["创建快"]
  disk --> fast
  cmd --> usable["环境可用"]
  inc --> state["状态可保存、可回滚"]
~~~

### 1. 内存：快照文件、MAP_PRIVATE、memslot 和按需恢复

传统启动路径是：

~~~text
分配内存 → 引导内核 → 启动服务 → agent 就绪
~~~

v0.7.2 的 fast-restore 路径可以这样理解：

~~~text
模板 memory snapshot file（或其 reflink 派生文件，按实现）
        ↓
VMM 打开快照文件
        ↓
mmap(MAP_PRIVATE, prefault=off) → KVM memslot
        ↓
guest 首次访问时 fault，页面按需从 page cache / 文件读取
        ↓
写入某页时变成当前 VMM 的私有页
        ↓
agent 经 vsock 就绪
~~~

这里必须避免一个常见误读：

> **MAP_SHARED 不是写时复制开关。**  
> 当前 fast-restore 的关键路径是把快照文件按 MAP_PRIVATE 映射，再让 KVM memslot 指向这段映射；MAP_SHARED 主要用于需要跨宿主进程共享 guest RAM 的 memory-zone / vhost-user 等场景。最终隔离依赖具体的恢复映射和 CoW 路径，而不是某个 flag 的名字。

~~~mermaid
flowchart LR
  file[("模板快照 backing<br/>或 reflink 派生文件（按实现）")]
  file --> ma["VM A<br/>mmap(MAP_PRIVATE)<br/>KVM memslot"]
  file --> mb["VM B<br/>mmap(MAP_PRIVATE)<br/>KVM memslot"]
  ma --> fa["A 首次访问<br/>fault → 按需读入"]
  mb --> fb["B 首次访问<br/>fault → 按需读入"]
  ma --> wa["A 写入某页<br/>私有 CoW 页"]
  mb --> wb["B 写入某页<br/>私有 CoW 页"]

  shared["MAP_SHARED<br/>跨 host 进程共享 RAM / vhost-user<br/>不是 fast-restore 默认隔离路径"]
  shared -.-> file
~~~

这就形成“**逻辑上独占、物理上尽量共享**”：

- 每个 guest 有自己的内核视角、设备状态和工作集。
- 模板只读页、文件 page cache 和未写入的快照数据可以复用，但实际共享程度取决于快照文件、映射方式、文件系统和内核回收行为。
- 任一实例写入后，写页进入该实例的私有工作集，不回写模板快照。

### 2. 磁盘：FICLONE 先复制元数据

下面只画本地 reflink backend；S3 / 对象存储路径是另一套远端 CoW 机制。

~~~mermaid
flowchart LR
  root[("20 GiB 模板卷")]
  root -->|FICLONE / reflink| a["沙箱 A<br/>共享 extent"]
  root -->|FICLONE / reflink| b["沙箱 B<br/>共享 extent"]
  root -->|FICLONE / reflink| c["沙箱 C<br/>共享 extent"]
  a -->|首次写入| ac["A 的新 extent"]
  b -->|首次写入| bc["B 的新 extent"]

  zero["创建阶段：主要是 extent / 引用计数元数据"]
  later["运行阶段：写热点、碎片、快照链会产生真实 IO 与空间成本"]
  zero -.-> a
  later -.-> ac
  later -.-> bc
~~~

所以“20 GiB 模板派生 1000 份”不等于立刻写入 20 TiB；但也不能把 FICLONE 理解成所有后续成本都消失。

### 4. 增量快照：Full、Incremental、SoftDirty

源码里可以确认三类 SnapshotType。差异不是“快照是否完整”，而是“如何找到这次需要写入的变化”：

~~~mermaid
flowchart LR
  full["Full<br/>保存完整内存状态"] --> fcost["代价高<br/>语义最保守"]
  inc["Incremental<br/>pagemap bit 61<br/>识别匿名 / CoW 页"] --> icost["依赖父级基线<br/>通常是累计变化集合"]
  soft["SoftDirty<br/>pagemap bit 55<br/>clear_refs 后的写入窗口"] --> scost["依赖内核能力与清理时序<br/>不支持时可能退化到 Incremental"]
~~~

| 模式 | 变化判断 | 主要代价 | 需要特别留意 |
|---|---|---:|---|
| Full | 不判断，保存完整状态 | 高 | 简单、容量和写入时间更重 |
| Incremental | 依赖匿名页与已有 CoW 基线 | 中 | 父级基线和恢复映射必须一致 |
| SoftDirty | 匿名页与 soft-dirty 页的交集 | 低到中 | 依赖内核能力、清理时序和并发正确性 |

恢复时仍要把父级基线、磁盘状态、内存状态、VMM 设备状态和元数据组合起来。**“只保存变化页”不等于“快照逻辑上只包含变化页”。**

## 三、治理语义：一毫秒不省，但没有它没人敢用

供给语义在做减法：少引导、少拷贝、少驻留。治理语义在做加法：加策略、加审计、加凭据控制。

~~~mermaid
flowchart TB
  guest["guest / Agent"]
  tap["TAP 网卡"]
  vs["CubeVS<br/>eBPF 快速路径"]
  policy[("pinned BPF maps<br/>设备注册·会话·CIDR·DNS TTL")]
  egress["CubeEgress<br/>命中规则时的 L7 代理"]
  secret[("凭据策略<br/>按请求注入")]
  audit[("审计事件<br/>sandbox_id · tenant_id · policy_version")]
  world["外部 API / Git / 网络"]

  guest --> tap --> vs
  policy <--> vs
  vs -->|L3/L4 允许，未命中 L7| world
  vs -->|命中 HTTP/HTTPS L7 规则| egress
  egress <--> secret
  egress --> world
  vs --> audit
  egress --> audit
  guest -. "私网 / 未授权地址" .-> blocked["内核路径拒绝"]
  vs -.-> blocked
~~~

四件事最关键：

1. **CubeVS 做 L3/L4 快速治理**：TAP、NAT、连接跟踪、CIDR allow/deny、DNS 学习等尽量在内核路径完成。
2. **CubeEgress 做按需 L7 治理**：只对命中 HTTP/HTTPS 规则的请求检查域名、SNI、Host、方法、路径并注入凭据。
3. **凭据不作为沙箱环境变量下发**：沙箱发起请求，出口侧按策略临时注入；审计记录关联句柄和策略版本，而不是把真实凭据写入日志。
4. **租户和生命周期也是治理**：配额、销毁留证、策略版本和审计保留期决定系统能否被企业接纳。

治理语义的判据很简单：

> 砍掉快照恢复，创建速度的关键路径会改变；砍掉凭据注入，创建仍然可以发生，但生产安全边界不成立。

### 两种热加载：状态热保存 vs 规则热更新

~~~mermaid
flowchart LR
  subgraph supply["供给语义热加载：保存状态"]
    pause["暂停 vCPU / 设备"]
    snap["写入 Full / Incremental / SoftDirty 快照"]
    resume["原地 resume / rollback"]
    clone["从同一状态 clone 新沙箱"]
    pause --> snap --> resume
    snap --> clone
  end

  subgraph govern["治理语义热加载：修正规则"]
    prog["eBPF 程序持续运行"]
    map["更新 pinned BPF map"]
    allow["CIDR / 域名 / 租户策略生效"]
    prog --> map --> allow
  end
~~~

两边都追求“不重启”，但保存的对象不同：

- 供给热加载保存 **状态**，让世界可以被挂起、恢复、分叉。
- 治理热加载保存 **规则**，让世界可以被收紧、放行、审计。

## 四、一次 Sandbox 创建：十步看懂创建路径

~~~mermaid
sequenceDiagram
  autonumber
  participant SDK as SDK / Agent
  participant API as CubeAPI
  participant M as CubeMaster
  participant R as Redis
  participant L as Cubelet
  participant C as CubeCoW
  participant H as CubeShim + Hypervisor
  participant N as CubeVS / CubeEgress
  participant G as guest agent

  SDK->>API: create sandbox
  API->>M: 鉴权后转成调度请求
  M->>R: 读取节点水位、模板命中与租户配额
  R-->>M: 返回候选节点
  M->>L: 下发 NodeB 创建指令，写入中间状态
  L->>C: FICLONE 派生 rootfs / 工作卷
  C-->>L: 返回卷与快照基线
  L->>H: 建立 VM、恢复内存与设备状态（可与网络初始化并行）
  L->>N: 创建 TAP，写入该沙箱策略 map（并行初始化）
  N-->>L: 网络路径就绪
  H->>G: guest 经 vsock 启动 / 握手
  G-->>L: agent ready / health check（依赖 VM 与网络）
  L->>R: 上报成功与资源水位
  R-->>M: 状态变为 running
  M-->>API: 返回 sandbox_id
  API-->>SDK: sandbox ready
~~~

### 怎么读这条链路

- 控制面主要在 **鉴权、调度、写状态、返回结果**。
- 供给与继承平面主要在 **卷派生、VM 恢复、guest agent 就绪**。
- 治理语义在网络初始化时写入策略，但之后还会在每次出站请求上持续工作。
- 典型的热节点、模板本地命中、无排队路径里，创建时间才可能接近公开的“约 60ms”目标；冷启动、跨节点恢复、镜像拉取、并发排队和首次触碰页面都会改写数字。

~~~mermaid
flowchart LR
  cp["控制面<br/>鉴权·调度·状态"] --> data["数据面<br/>FICLONE + 内存恢复"]
  data --> ready["网络策略 + agent<br/>达到可执行"]
  data -. "共同原因：不从零开始" .-> reason["复用模板、快照和共享 backing"]
~~~

> **口径卡：**
>
> - “约 60ms”是项目公开的体验目标/特定 happy path 锚点，不是所有节点、模板、并发度和计时起点下的 SLA。
> - “约 5MB”必须先说明是 VMM 线程、RSS、PSS、USS、cgroup memory，还是独占页增量，不能直接写成“每个完整沙箱只占 5MB”。
> - Firecracker 的“约 125ms”是特定硬件、1 vCPU、128 MiB 配置下，从 InstanceStart API 到 guest init 的测量目标，不能当成所有 MicroVM 的理论上限，也不能与 CubeSandbox 的端到端恢复数字直接比较。

同一个系统的 P95 也会被并发改写。官方基准中，串行创建和高并发创建不是同一条曲线；因此图里标出的 60ms 只能解释热路径的形状，不能拿来直接换算集群容量。

| 观察口径 | 示例结果 | 应该怎样读 |
|---|---:|---|
| CubeSandbox 串行创建 P95 | 约 57.4ms | 热模板、特定硬件与计时口径下的端到端结果 |
| CubeSandbox 50 并发创建 P95 | 约 508ms | 排队、IO 争用和资源窗口会进入尾延迟 |
| Firecracker InstanceStart → guest init | 目标不超过 125ms | 另一套起止点和规格，适合做参照，不适合直接相减 |

## 五、沙箱运行之后：四层继续协作

| 运行时刻 | 主要负责平面 | 发生了什么 |
|---|---|---|
| Agent 执行代码 | 继承平面 | guest 独立内核执行，敏感操作由 VM exit/VMM 处理 |
| Agent 请求外部 API | 治理语义 | CubeVS 先做 L3/L4 判断，命中规则时由 CubeEgress 注入凭据并审计 |
| 恶意代码扫私网 | 治理语义 | 默认拒绝规则在数据路径阻断，包不能直接抵达目标 |
| 第 20 步改坏环境 | 供给语义 | rollback 到第 15 步快照，保持沙箱身份语义 |
| 等待用户确认数小时 | 供给语义 | AutoPause 保存状态、释放驻留内存，之后 resume |
| 平台更新网络策略 | 治理语义 | 更新 eBPF map，程序和其他沙箱不必重启 |
| 新租户上线 | 控制平面 | 配额、策略版本、审计绑定进入状态库 |
| 节点故障 | 控制平面 + 供给语义 | Redis 保存控制面元数据；只有快照字节已上传并标记 remote-ready 时，才具备跨节点恢复条件 |

生命周期可以简化成：

~~~mermaid
stateDiagram-v2
  [*] --> Creating
  Creating --> Running: guest ready
  Creating --> Failed: 超时 / 资源不足 / 恢复失败
  Running --> Pausing: AutoPause / 用户 pause
  Pausing --> Paused: 停 vCPU → 保存快照 → 释放驻留
  Paused --> Resuming: resume
  Resuming --> Running: 恢复成功
  Running --> RollingBack: rollback
  RollingBack --> Running: 基线恢复
  Running --> Cloning: clone
  Cloning --> Running: 新 sandbox_id
  Running --> Terminated: delete / TTL
  Paused --> Terminated: TTL / delete
  Failed --> Terminated: 清理完成
~~~

注意：pause / snapshot / resume 是一个有明确暂停窗口的状态操作，不应画成“完全不停机”；当前实现和基准路径可能是全量内存拷贝，是否使用增量能力要看配置和内核能力。

Rollback 和 Clone 也不是一回事：

- **Rollback**：同一个 sandbox_id 回到某个内部快照；外部 API 已产生的副作用不会自动回滚。
- **Clone**：从某个状态派生新身份；文件、内存、网络、凭据和审计都要重新隔离。

## 六、把整篇压成四句话

1. **继承平面**回答“如何安全地造一台薄 VM”：KVM、RustVMM、最小设备、PVH 和进程隔离给出硬件边界与速度下限。
2. **供给语义**回答“有状态环境如何快速出生、复用、回滚和挂起”：FICLONE、内存快照、vsock 和增量页追踪把启动改造成恢复。
3. **治理语义**回答“凭什么敢让模型联网并执行代码”：CubeVS、CubeEgress、凭据控制、策略热更新和审计把网络改造成一份有边界的合同。
4. **控制平面**回答“成千上万个沙箱同时存在时谁来做决定”：CubeAPI、CubeMaster、Redis 和模板中心把状态、调度和规模解耦。

> **最终记忆点：削薄是继承的，速度是供给的，敢用是治理的，规模化靠分离。**
