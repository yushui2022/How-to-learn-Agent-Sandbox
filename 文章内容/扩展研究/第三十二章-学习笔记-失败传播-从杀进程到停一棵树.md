## 引子：单体的死法 vs 树的死法

单 Agent 世界的失败很简单：进程死了，任务失败，重开一个。故障的传播路径只有一条——从进程到任务报告。你可以 kill -9，可以重启，可以整个丢掉重来，因为只有一个执行环境、一份状态、一个责任主体。

多 Agent 世界把这件事彻底改写了。第二十章的判断："多 Agent 系统是一棵资源和状态树"——树的每个节点都可能死，而**一个节点的死法有三种后果**：

1. **无效死亡**：该停的兄弟没停，白烧 token 和沙箱配额；
2. **过度死亡**：不该停的兄弟被连坐，已完成的工作全部作废；
3. **危险死亡**：死前留下的外部副作用（订单、支付、邮件）没人知道怎么处理。

失败传播的全部工程，就是让每一个节点的死都落在"恰当死亡"的位置上——该停的停、不该停的活着、外部世界有交代。本章按"立法（预算树）→ 执法（级联终止）→ 判后（部分成功）→ 外交（外部副作用）→ 发散（更大的图景）"五段展开。

## 一、预算树：先立法，后办事

### 1.1 防的是什么：乘法爆炸

第二十章第一节埋的公式在第四节兑现为法律：

```text
N_running ≤ min(N_token_budget, N_sandbox_quota, N_node_capacity)   （并行度约束）

Σ child_time_budget    ≤ parent_time_budget                          （预算树三不等式）
Σ child_sandbox_quota  ≤ parent_sandbox_quota
Σ child_egress_budget  ≤ parent_egress_budget
```

**为什么必须立法**：8 个 worker 每个都按自己的默认上限运行（比如各 10 分钟 TTL、各 2GB 内存、各 100 次 API 调用），父任务的实际消耗就是 8 倍上限——这不是异常，是**默认行为的乘法**。第二十章那句"父任务剩余 30 秒，不能再给新 worker 60 秒的独立 TTL"，说的就是：**没有预算树，每个子任务的"合理默认"相加就是父任务的不合理灾难。**

### 1.2 预算的四个维度（发散）

第二十章列了 token、时间、沙箱、出口四类预算。值得发散的是：这四类的**失败形态**完全不同，治理手段也不同。

| 预算维度 | 超了会怎样 | 能否事后补救 | 治理手段 |
|---|---|---|---|
| **Token 预算** | 成本爆炸（钱） | 不能——花掉的推理费收不回 | 事前硬限：调用层计数熔断 |
| **时间预算** | 尾延迟无界（体验） | 部分——可中途取消止损 | 软硬超时：软超时收尾、硬超时终止（第十七章分层超时） |
| **沙箱配额** | 资源占用（密度） | 能——销毁即释放 | 配额记账：四级上限（全局/租户/父任务/拓扑层） |
| **出口预算** | 外部副作用（危险） | 最难——副作用已发生 | 事前审批：网关侧按策略注入与限额（第七/十章） |

**发散观察**：四个维度按"可逆性"排序是 沙箱 > 时间 > token > 出口——**越靠后的越必须事前治理**。这解释了为什么治理语义（凭据、审批、策略）在系列里的地位一路上升：它管的恰好是最不可逆的那个维度。第十章的注入式凭据、Muse 的 Sentinel 全量审批，本质上都是在出口维度上"事前立法"。

### 1.3 预算树的经济学亲缘（发散）

预算树不是 Agent 时代的新发明，它有三个著名的亲：

1. **数据库的查询预算**：`statement_timeout`、`max_execution_time`——单条查询不能拖垮整个实例；
2. **分布式追踪的 deadline propagation**：gRPC 的 per-request deadline 沿调用链向下传递，每一跳用剩余时间做自己的超时——"父任务剩 30 秒不能给子任务 60 秒"就是这条原则；
3. **操作系统的资源层级**：cgroup 树本身就是预算树——子 cgroup 的限额之和受父 cgroup 约束。第二十六章讲过的双层资源模型（host cgroup + KVM memslot）是它在沙箱层的实现。

**发散判断**：Agent 编排框架（LangGraph、Dynamic Workflow）正在把这三个传统悄悄合流——工作流引擎的节点预算 ≈ 查询预算，节点间传递的剩余时间 ≈ deadline propagation，沙箱配额 ≈ cgroup 层级。**预算树是 cgroup 思想在任务层的复活。**

## 二、级联终止：执法的五步曲与一个判断

### 2.1 标准动作：标记 → 取消 → 宽限 → 销毁

第二十章给出的终止序列，每一步的存在理由：

| 步骤 | 为什么必须有 |
|---|---|
| ① 标记状态 | 不标记就发取消，审计轨迹里这个 worker 的最后状态是"运行中"——复盘时无法区分"正常完成"与"被终止" |
| ② 发送取消 | 给 worker 一个收尾机会：flush 输出、上传部分 artifact、释放外部连接 |
| ③ 等待宽限期 | 取消信号到达 ≠ 进程立即停止；宽限期是给"优雅退出"的合同（对照 K8s 的 `terminationGracePeriodSeconds`） |
| ④ 销毁沙箱 | 宽限期过后强制回收——这是底线，不依赖 worker 自觉 |
| ⑤ 确认与记录 | 销毁请求本身也可能失败（节点失联）；"已请求销毁"与"已确认销毁"是两个状态（第二十九章状态机的单向失败原则） |

**发散对照——Kubernetes 的同款设计**：Pod 终止 = 发 SIGTERM → 等 grace period → 发 SIGKILL → 确认 Finalizers 清空。两个系统在互不知情的情况下收敛到同一条序列，因为**优雅终止的约束是普适的**：强杀太粗暴（丢状态）、不杀太危险（僵尸资源）、所以只能"先礼后兵 + 兜底"。

### 2.2 最难的判断：兄弟 worker 停不停

第二十章第 96 行的核心规则：

> 兄弟 worker 是否停止取决于依赖：独立搜索可以继续，依赖同一中间结果的审查 worker 应取消。

翻译成图论语言：**终止沿依赖边传播，不沿兄弟边传播**。

```
        parent
       /   |   \
   搜索A  搜索B  分析C
              |
           审查D（依赖 C 的产出）
```

- C 死了 → D 必须取消（D 的输入永远等不到了，继续跑是纯浪费）；
- C 死了 → A、B 不受影响（它们的产出独立有效）；
- **错误设计**：orchestrator 一看到 C 死就 panic 全停——这是"过度死亡"，三个有效结果陪着浪费。

**发散判断**：这个规则的执行前提是**依赖图必须显式存在**。依赖信息藏在模型上下文里（"我觉得 B 应该等 A"）时，终止判断退化为主 Agent 的临场猜测——你的工作流语料里 A 类故障（Agent 自行缩小任务范围）在失败传播领域的镜像就是"Agent 自行决定连坐范围"。**工作流引擎把 DAG 写进代码，终止传播才变得可推导。**这是"编排搬进代码"的第三重价值（前两重：状态外置、需求可预测——见第三十章场景 A）。

### 2.3 幂等：执法武器的保险栓

第二十章第 96 行末的警告："终止事件必须幂等，因为控制面重试可能重复发送。"

为什么控制面一定会重试？因为它自己也在分布式世界里——取消请求发出去后网络抖动、超时、组件重启，发送方无法区分"对方没收到"和"对方收到了但响应丢了"，唯一安全的动作是重发。于是 worker 和 sandbox 可能收到两次、三次 Cancel。

**幂等键在本章的第四张面孔**：回滚用它（第二十九章）、供给重试用它（第十八章）、跨沙箱通信用它（第三十章）、终止执法还用它。一个多 Agent 系统里幂等键出现的密度，就是它的分布式成熟度。

## 三、部分成功：最反直觉的一条纪律

### 3.1 场景与直觉的冲突

三个 worker 成功、第四个失败。直觉给出两个方案：

- 方案一（全局一致）："全部重跑"——干净、简单、结果确定；
- 方案二（部分成功）："保留三份成功产出，只重跑失败分支"——省资源，但要处理"混合时间线"。

第二十章选了方案二，并给出了完整纪律：保存成功 artifact 与失败 reason，只重跑失败分支，**汇总 Agent 要知道哪些结果来自重试、哪些来自原始执行**。

### 3.2 为什么"全部重跑"是陷阱

1. **浪费乘法**：重跑三个已成功的 worker = 3 倍的 token、时间、沙箱开销——预算树在失败场景下的第一次考验，"全部重跑"直接把成本乘回去；
2. **非确定性放大**：LLM worker 不是纯函数，重跑成功分支会得到**不同**的结果（不同的采样、不同的中间状态）——你以为在重跑，其实在掷骰子。原来那三份成功产出的价值不在于"可以再生成"，而在于"它们已经存在且通过了下游检验"；
3. **外部副作用风险**（下一节的主角）：重跑一个已经下过订单的 worker，如果没有幂等键，就是重复下单。

### 3.3 混合时间线的审计责任

部分成功的隐藏成本：最终交付物里混着"原始执行"和"重试执行"的结果，两者产生于不同的时间、可能基于不同版本的模板或策略。第二十章要求汇总 Agent 知晓来源——落到工程上就是 **artifact 元数据必须携带执行世代（generation）**：第几次执行、从哪个快照出生、哪个策略版本放行。这与第十七章的 manifest（模板 digest、模型版本、评分器版本）是同一个纪律在不同场景的应用：**可复现的前提是可追溯，可追溯的前提是元数据齐全。**

## 四、外部副作用：沙箱管不到的世界

### 4.1 红线的完整版

第九章教过"沙箱回滚不是时间旅行"：沙箱内部状态可以回退，外部世界（TCP 连接、数据库事务、已发送的邮件、已上传的文件）不会跟着回滚。第二十章第 100 行把它推到多 Agent 场景，并升级成行动纪律：

> 不要为了"全局一致"把已完成的外部副作用自动回滚，除非业务具备补偿事务。

### 4.2 补偿事务：Saga 模式的 Agent 版（发散）

"补偿事务"在分布式系统里有一个成熟的名字：**Saga 模式**。把一个分布式事务拆成本地事务序列 T1, T2, ..., Tn，每个 Ti 配一个补偿动作 Ci；如果 Tk 失败，反向执行 Ck-1, ..., C1 抵消前面的影响。

经典例子（订机票行程）：

```text
T1 订航班 → T2 订酒店 → T3 租车
若 T3 失败：C2 取消酒店 → C1 取消航班
```

**Agent 场景的同构**：

```text
worker A：向供应商系统询价并锁价（外部副作用）
worker B：比价分析（内部）
worker C：按 A 的锁价下单（外部副作用）
若 B 失败：A 的锁价需要释放（补偿：调供应商的解锁接口）；
        C 还没执行，无需补偿——这正是"终止沿依赖边传播"的价值：
        及时取消 C，避免了最昂贵的补偿（退单）。
```

**发散判断——Saga 与预算树的合谋**：好的失败传播设计里，**级联终止是补偿的前置防线**。越早沿依赖边取消未执行的分支，需要补偿的外部副作用越少。终止快一秒，可能省掉一次退单。"先礼后兵"的五步终止序列里，宽限期（第③步）正是在给"还来得及取消的外部操作"留窗口。

### 4.3 两阶段提交为什么不行（发散）

有人会问：为什么不直接用 2PC（两阶段提交），把所有外部操作做成原子事务？三个原因：

1. **参与者不可控**：供应商系统、支付网关、邮件服务不会实现 prepare/commit 协议——外部世界没有"准备好但先不生效"的通用接口；
2. **阻塞风险**：2PC 在协调者故障时把所有参与者锁死在 prepare 状态——对 Agent 系统，这等于一棵树因为一个 worker 卡死而全员冻结；
3. **语义不匹配**：LLM worker 的"执行"不是数据库写——没有 abort/rollback 的原生对应物。

所以 Agent 系统的事实答案就是 Saga：**接受副作用不可原子化，用补偿换最终一致。**这与微服务架构二十年的演进结论完全一致——不是 Agent 发明了新问题，是 Agent 把微服务的老问题搬进了新战场。

## 五、发散：失败传播的更大图景

### 5.1 与过载分级的对称性

第十八章的系统级过载分级（排队 → 提示 → 降级 → 拒绝 → 熔断）与本章的任务级失败传播，是一对**镜像设计**：

| | 系统级（第十八章） | 任务级（本章） |
|---|---|---|
| 保护对象 | 平台本身 | 任务树 |
| 第一反应 | 排队缓冲 | 标记状态 |
| 升级手段 | 降级/拒绝/熔断 | 取消/级联终止 |
| 底线 | 宁可拒绝不雪崩 | 宁可部分成功不全部作废 |
| 依赖的信息 | 水位、队列、槽位 | 依赖图、预算树、执行世代 |

**发散判断**：两层之间需要打通——任务级熔断应该向系统级传导（一个父任务的失败率异常，应该影响调度器对同类任务的派发），系统级过载也应该向任务级传导（节点紧张时，预算树的配额自动收紧）。第二十一章"降级目标是把故障半径限制在节点或租户"说的就是这种跨层传导的设计意图。**成熟平台的标志不是每层各自为政，而是故障信息跨层流动。**

### 5.2 Sentinel：失败传播的"事前形态"（发散）

Muse 的 Sentinel（第三十一章讨论过的监督 Agent）与本章是什么关系？表面看它管的是"审批"不是"失败"——但换个角度：

- 级联终止是**事后执法**：坏事已经发生，止损、隔离、善后；
- Sentinel 审批是**事前执法**：每个出网动作先过审，坏副作用在发生前被拦下。

两者在"外部副作用"维度上恰好互补：**能事前审批的（出网请求）走事前；事前拦不住的（长时任务的资源消耗、外部世界的意外响应）靠事后终止与补偿兜底。**一个完整的失败治理体系，两条腿都要有。这也解释了为什么 Muse 敢让 Agent 替用户下单——不是因为它信任模型，而是因为最危险的维度（出口）被事前管住了，剩余风险才落在可接受区间。

### 5.3 失败归因：终止之前的最后一问（发散）

第十七章的失败四分类（模型失败/环境失败/基础设施失败/判定失败）在多 Agent 场景升维：**树里每个节点的失败都要带着类别传播**。

- 模型失败 → 只重跑该分支（换策略或换采样种子）；
- 环境失败 → 从同一快照重派（环境问题环境解，第二十章第三节快照派生的失败场景）；
- 基础设施失败 → 换节点重派，且要计入平台 SLO（第十八章的重试/拒绝率按 reason code 分类）；
- 判定失败 → 保留原始 artifact，修评分器后重新判定（**绝不重跑 worker**——执行无错，判定有错）。

**发散判断**：四类失败对应四种重跑策略，说明"重跑"不是同质动作——**无差别重试是失败治理的初级形态**。你的工作流语料里"模型失败不应与环境失败采用同一重试策略"，正是这条纪律的实战版。而这四类归因能自动执行的前提，又一次回到显式化：失败发生时，系统必须能区分"沙箱没起来"（基础设施）和"代码跑了但断言失败"（模型）——这需要执行轨迹（第十三章）与供给链路（第十八章）的观测数据在任务树上关联。**失败归因是全系列观测能力的最后考试。**

### 5.4 从"停一棵树"到"养一片林"（发散收尾）

第二十章的容量账：200 个并发父任务 × 8 worker = 1,600 个沙箱。失败传播在这个规模下还有最后一层含义：**不是每棵树都值得救**。

- 低价值任务树（探索性实验、低价租户的批处理）：失败即整树销毁，资源留给高价值树——这是失败传播的经济学维度；
- 高价值任务树：部分成功 + 分支重跑 + 补偿善后，全套纪律上齐；
- 判据回到预算树：**任务树的"抢救预算"也应该是预算的一个维度**——花 30% 的原始成本救回一棵树值得，花 300% 就不如重开。

这引出本章的收尾判断：失败传播的终极形态不是任何具体机制，而是**把"失败"从异常变成预算内的常规事件**——每次失败都有类别、有代价、有预案、有记录；树死得起，林活得成。到这一步，多 Agent 系统才真正从 demo 变成生产系统，与第二十一章"生产化的单位是可回滚的交付链"完成闭环。

## 企业视角

**给平台团队**：预算树的四级上限（全局/租户/父任务/拓扑层）是容量治理的任务级抓手；把"失败率按 reason code 分类"接进第十八章的 SLO 面板，两张图合成一张容量-故障联动视图。

**给安全团队**：外部副作用清单（下单、支付、发邮件、写生产库）应该像资产清单一样管理；每个副作用标注补偿动作与幂等键字段——出事时按清单处置，不靠临场发挥。第二十一章"怀疑被入侵的沙箱不要直接销毁"在本章的延伸：销毁前先取证，补偿动作也在证据链里。

**给业务团队**："部分成功"改变了交付语义——报告必须标注混合时间线（哪些来自重试）。对下游消费者（包括另一个 Agent）而言，一个不声明世代来源的"成功"结果，比一个诚实的"部分成功"更危险。

## 本章小结

| 关键认知 | 一句话 |
|---|---|
| 树的三种死法 | 无效死亡（该停没停）、过度死亡（不该停连坐）、危险死亡（副作用无交代）——失败传播就是让每个死都恰当 |
| 预算树 | 防默认行为的乘法爆炸；四个维度按可逆性排序，越不可逆越要事前治理 |
| 级联终止 | 标记→取消→宽限→销毁→确认；终止沿依赖边传播，不沿兄弟边；终止事件必须幂等 |
| 部分成功 | 全部重跑是陷阱（浪费乘法+非确定性+副作用风险）；混合时间线要有执行世代 |
| 外部副作用 | 沙箱管不到的世界用 Saga 补偿；级联终止是补偿的前置防线——取消快一秒可能省一次退单 |
| 2PC 不可行 | 参与者不可控、阻塞风险、语义不匹配——Agent 复用了微服务二十年的结论 |
| 两层镜像 | 系统级过载分级与任务级失败传播互为镜像，成熟平台的标志是故障信息跨层流动 |
| 事前与事后 | Sentinel 式审批管事前，级联终止管事后；出口维度两条腿都要有 |
| 失败归因 | 四类失败对应四种重跑策略；无差别重试是失败治理的初级形态 |
| 终极形态 | 把失败从异常变成预算内的常规事件——树死得起，林活得成 |

## 思考题（能算账的那种）

1. 一棵任务树有 12 个 worker，其中 3 个产生外部副作用（锁价、下单、发通知），补偿成本分别为 5、50、5 个成本单位；重跑一个内部 worker 的成本是 2。某次基础设施故障导致 4 个内部 worker 失败。比较"全部重跑"与"只重跑失败分支"的总成本（含已成功分支的重跑与副作用补偿），并说明依赖图结构如何改变答案。
2. 为 5.4 节的"抢救预算"设计一个公式：给定树的价值 V、原始成本 C、已完成比例 p、部分成功重跑成本 R，给出"值得抢救"的判定条件，并讨论 V 无法用钱衡量时（如交付合同）公式怎么退化。
3. worker A 已向供应商锁价后超时。设计任务树状态、幂等键方案与补偿流程，要求：重试不重复锁价、最终要么下单要么释放锁价、审计可回答"锁价存在了几分钟"。

## 下章预告

失败传播完成时，任务树在任何故障下都能有序收敛。但树与树之间的秩序——多租户的公平、洪峰的错峰、资源的弹性——是另一个战场：那是第十八章与第十九章的主场，也是把第三十、三十二章的纪律放进集群规模检验的地方。
