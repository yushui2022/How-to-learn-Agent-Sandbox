## 引子：多 Agent 系统的第一批设计决策

第二十章把多 Agent 系统定义为"一棵资源和状态树"。树的形状由拓扑决定（第 30 章姊妹篇覆盖拓扑谱系），但树要活起来，还要回答两个更贴近日常工程的问题：

1. **节点之间怎么说话**——worker 怎么拿到任务、结果怎么回来、主 Agent 怎么指挥工具沙箱；
2. **节点之间怎么共享记忆**——多个 worker 是否看到同一份文件、改了一半的状态谁可见、合并谁来定。

这两个问题看似是"选个中间件"的工程小事，实际上是**治理语义在应用层的落地**。选错通道或选错状态模型，安全上会自己打通隔离边界，成本上会把协调开销放大到业务不可用。本文把这两个决策空间各自摊开，给出选型框架和纪律清单。

贯穿全文有一条隐藏的排序线，先立在这里：

> **通信与状态的所有选项，都排在一条从"快而隐式"到"慢而明确"的谱上。越明确越可审计，越可审计越慢越贵。选型不是找最好的，是在谱上找你的业务该站的位置。**

```
快而隐式 ──────────────────────────────────► 慢而明确
vsock → 出口网关 → 共享文件 → 消息传递
（血管）  （海关）   （白板）    （公文）
```

## 第一部分：通信通道——四个选项的完整决策空间

### 1.1 先纠偏：vsock 不是你以为的那个网络

**vsock 是什么**：virtio-vsock 提供的、guest 内进程与宿主进程之间的 socket 通道。在 CubeSandbox 里，它是 CubeShim 指挥 guest 内 cube-agent 的血管——命令下发、结果回传、心跳、生命周期协调全走这里。

**最常见的误解**："两个沙箱都支持 vsock，所以它们可以用 vsock 互相通信。"——**错，而且是有害的错**。vsock 的通信两端是 **host ↔ guest**，不是 VM ↔ VM。两台 MicroVM 要互相说话，必须在中间显式搭桥：host 上的转发代理、虚拟交换机的路由、或者一个消息系统。而桥一旦搭起来，身份与审计就要重新设计——原来"一个沙箱对宿主"的关系，变成了"沙箱对沙箱"的网状关系，每条边都要回答"你是谁、凭什么"。

**为什么这个纠偏值得单独立一节**（第二十章原文专设一小节的原因）：

1. **安全边界上的"顺便"都是漏洞**。把 host↔guest 通道暴露给租户做应用层通信，等于让宿主机成为所有沙箱之间的中转站——宿主的攻击面被直接扩大。第七章反复强调的"沙箱是出口上的隔离舱"，在这里被自己拆了。
2. **框架文档的暗示不等于底层事实**。不少多 Agent 框架的示例假设"Agent 之间可以低层互通"，那是因为示例跑在本地进程或受控网络里；换到 MicroVM 架构，这个假设悄悄失效了。第二十章基线说明里专门写了这句：**"不把示例拓扑或 SDK 名称当成底层网络实现"**——这是全系列口径纪律在多 Agent 章的落地。

**vsock 的正确位置**：基础设施的血管（agent 通道、控制面 sidecar、宿主代理），不是应用层的高速公路。应用层的多沙箱协作，往谱的右边走。

### 1.2 出口网关：把"能说话"变成"可治理地说话"

沙箱的出站流量经过策略网关（CubeSandbox 里就是 CubeVS + CubeEgress 的组合：内核态 eBPF 管三层连通，L7 网关管域名、路径与凭据注入）。多 Agent 场景下，这条路承担"worker 之间的受控网络"角色。

**买到的三样东西**：

1. **可观察**——每次跨沙箱通信都有记录：谁、何时、访问了什么、被哪条策略放行；
2. **可撤销**——策略一改即断，不需要"通知对方下线"；
3. **可插凭据代理**——worker A 请求 worker B 的服务，真实密钥在网关侧注入，A 的上下文里只有占位符（第十章的机制直接复用）。

**付出的三样代价**：每一跳的延迟（策略查表 + 代理转发）、网关的单点压力（这又是第十八章的供给问题）、连接状态管理（会话表、NAT、超时）。

**一条铁律**（第二十章第 48 行，值得抄进每个设计文档）：

> **跨 worker 的请求应包含任务树、发送者、接收者、过期时间和幂等键。不要只用 IP 地址鉴权，因为 sandbox 重建后 IP 可能变化，且 IP 不是租户身份。**

拆开理解这五个字段为什么缺一不可：

| 字段 | 回答的问题 | 缺了会怎样 |
|---|---|---|
| 任务树（父任务 ID + 路径） | 这个请求属于哪棵树 | 审计时无法按任务聚合，失败传播找不到边界 |
| 发送者身份 | 谁发的 | IP 鉴权在沙箱重建后失效；伪造请求无法追责 |
| 接收者身份 | 发给谁 | 广播式调用，网关无法做最小权限 |
| 过期时间 | 请求多久算作废 | 排队中的陈旧请求被迟到执行，覆盖新状态 |
| 幂等键 | 重试算不算重复 | 控制面重试导致一次逻辑操作执行两次 |

**引申**：这五个字段组合起来，其实就是把第二十九章"状态机四铁律"（幂等、单向失败、可重试、可观察）翻译成了网络协议的字段清单。系列里反复出现的幂等键，在这里第三次出场——回滚有它、供给重试有它、现在跨沙箱通信还有它。**幂等键是多 Agent 系统的第一公民。**

### 1.3 共享文件系统：最快，也最容易出事

共享卷是 worker 之间交换代码和中间文件最自然的方式：挂一个目录，A 写 B 读，POSIX 语义，编译缓存、协同修改都顺手。**但它是四个通道里唯一一个"隔离边界会被自己打通"的**。

三个坑，每个都对应一类真实事故：

**坑一：半写状态**。worker A 正在写 `result.json`，worker B 读到了半截文件并开始处理——并发世界没有"写完了再给别人看"的默认保证。A 崩溃后留下的残缺文件，B 会当成合法输入。

**坑二：恶意污染**。一个被提示词注入操控的 worker 往共享目录放一个恶意脚本或符号链接（symlink 指向宿主敏感路径），兄弟任务读到就中招。**沙箱与沙箱之间的 KVM 墙挡不住共享卷上的内容流**——隔离边界在卷挂载点被合法地凿穿了。这不是假设：共享目录 + 自动执行（比如 `.bashrc`、`node_modules`、CI hook）的组合是经典攻击面。

**坑三：隐式耦合**。文件名和目录布局成了事实上的接口，但没有 schema、没有版本、没有 owner。谁重构了目录结构，谁就静默破坏了所有读这个目录的 worker——**没有契约的协作，改一行等于埋一颗雷**。

**使用纪律**（第二十章给出的完整清单）：

1. **目录所有权**——每个 worker 有自己的写入目录，公共目录只读；
2. **原子写入**——写临时文件 + `rename`，读者要么看到旧版要么看到新版，永远看不到半版；
3. **版本标记**——文件名或元数据里带版本，消费者校验版本再处理；
4. **锁**——需要互斥的地方显式加锁，不要依赖"应该不会同时写"；
5. **只读挂载**——对不可信 worker，能不给写权限就不给。**这是最强的一条：权限给出的越少，注入能造成的伤害越小。**

### 1.4 消息传递：一切显式，一切可重放

消息队列（或任何显式消息机制）把任务和结果变成一等公民：可持久化、可重放、可审计、可重试。

**买到的东西**：

- **异步解耦**——worker 不需要同时在线，任务进队列，worker 按自己的节奏领；
- **重试语义**——队列自带 ack、可见性超时（visibility timeout）、死信队列（DLQ）、幂等去重；
- **审计友好**——每条消息是一条完整记录，故障复盘时可以重放整条流。

**两条纪律**：

1. **消息里放 artifact 引用，不放大文件本体**。一条消息应该是 `{"input": "artifact://sha256:abc...", "task": "..."}` 而不是把 2GB 数据集塞进消息正文——队列是为小而频繁的元数据设计的，大载荷会拖垮吞吐和持久化；
2. **消息传递不自动保证文件一致性**。队列保证"消息送达"，不保证"消息引用的那个文件还在、还是那个版本"。artifact 仍然需要内容哈希寻址（content-addressable）——同一个 artifact 被 100 个 worker 使用时只存一份，哈希即身份，版本即内容。

**引申**：内容哈希寻址不是新发明——Git 的对象库、Docker 的镜像层、Nix 的 store 全是这个思想。多 Agent 的 artifact 管理本质上是**把构建系统的状态管理经验移植到 Agent 工作流**。评测平台的 manifest（第十七章）也是同一件事：结果必须能反查到产生它的输入。

### 1.5 四通道对照表（决策速查）

| | vsock | 出口网关 | 共享卷 | 消息传递 |
|---|---|---|---|---|
| **速度** | 最快（内核通道） | 中（每跳查策略） | 快（本地文件） | 慢（队列+存储） |
| **耦合** | 绑定宿主拓扑 | 绑定网络策略 | 最强（共享命名空间） | 最弱（只有消息契约） |
| **审计** | 弱（控制面日志） | 强（每次通信有记录） | 弱（只有文件系统日志） | 最强（消息即记录） |
| **身份** | host↔guest 固定 | 策略绑定沙箱身份 | 文件权限（粗粒度） | 消息字段显式携带 |
| **适用** | 控制通道 | 受控的业务网络 | 可信 worker 协作 | 异步任务、审计场景 |
| **一句话** | 血管 | 海关 | 白板 | 公文 |

**选型心法**：默认往右走（消息），有明确理由才往左走（延迟敏感且互信才用共享卷；控制面专用才碰 vsock）。**往左走的每一步都要用治理语义补偿**——共享卷配纪律清单，网关配五字段身份包。

## 第二部分：共享状态——三个模型，本质是"写权限放哪"

通信解决"说话"，状态解决"共同记忆"。三个状态模型的全部差异，可以用一句话钉死：

> **写入发生在哪里，一致性责任就落在哪里。**

```
共享卷：大家写同一块地       → 一致性靠纪律，责任在使用者
快照派生：出生一致、各写各的 → 一致性靠合并，责任在 orchestrator
消息+artifact：记忆外置      → 一致性靠契约，责任在协议设计
```

### 2.1 共享卷：一致性靠纪律

**适用**：编译缓存（写一次读多次，天然无冲突）、需要 POSIX 语义的任务（构建工具链大多假设文件系统）、小团队内互信 worker 的协同。

**成本结构**：锁竞争（写热点）、权限传播（谁有权限读谁的目录，要和治理语义对齐）、单点存储压力（共享卷的容量和 IO 成为全树的瓶颈——第十一章的账本方法在这里再次适用）。

**纪律**就是 1.3 节那五条。补充一条企业视角：**共享卷的权限模型必须和租户模型对齐**——跨租户的共享卷是数据泄露的直达通道。第二十一章 checklist 里"敏感租户与测试租户不共享默认策略"，落到状态层就是"不共享卷"。

### 2.2 快照派生：一致性靠合并

每个 worker 从同一模板或事件快照 clone 出发——第九章学过的机制：reflink 派生、出生即一致、写入私有。

**买到的两样**：

1. **天然隔离**——没有半写问题（各自写各自的副本），没有恶意污染（污染困在私有副本里）；
2. **天然可复现**——千个 worker 从同一基线出生，评测分数才反映模型能力而非环境差异（第十七章的正解）。

**新负担是合并**，第二十章第 66 行的红线：

> **合并冲突必须在 orchestrator 层解决，不能假设多个私有 rootfs 会自动合并。**

这句话值得展开理解。三个 worker 各自改了仓库的同一个文件、各自装了冲突版本的依赖、各自的内存里还有半完成的分析状态——这些差异**没有任何基础设施层面的机制**能让它们自动融合。合并是业务逻辑：Git 的 merge conflict 要人来解决，多 Agent 的 artifact 合并同样要 orchestrator（或专门的汇总 Agent）按业务规则来。**把合并责任下意识推给"系统"，是多 Agent 项目经典的翻车点。**

**典型场景**：批量评测（N 份派生，结果聚合无需合并工作区）、A/B 实验（各自独立，比较而非合并）、并行探索（多条方案各自跑完，择优采纳——合并退化为"选择"）。

### 2.3 消息 + artifact：一致性靠契约

worker 的全部输入输出都通过消息和 artifact 引用流动，谁也不碰谁的文件系统。

**买到的**：

- **最可审计**——每个 artifact 有哈希（身份）、有版本（历史）、有归属（谁产出）；"这个结论用了哪份数据"永远可答（第二十四章开放问题 5.5 安全证据链的应用层实现）；
- **最可重试**——失败分支重跑只需重新投递消息 + 重新引用同一 artifact，不依赖任何 worker 的本地状态；
- **存储最优**——内容哈希寻址天然去重，100 个 worker 用同一份输入只存一份。

**付出的**：序列化开销（一切都要变成消息和对象）、对象存储延迟（读 artifact 不如读本地盘快）、一致性延迟（"我发布了新版本"到"你看到了新版本"之间有窗口）。

**趋势判断**（引申）：**越严肃的系统越往这个模型收敛**。三个证据：其一，可复现评测要求 artifact 有 manifest（第十七章）；其二，你的工作流语料里"中间结果存 state 变量而不是模型上下文"——状态外置后约束不再丢失，正是这个模型的胜利；其三，第二十四章推测 B 的状态三分类（可重建/可迁移/不可复制），只有在记忆外置的结构下才能逐类管理。**共享卷是协作的便利设施，消息+artifact 是系统的责任结构。**

### 2.4 决策函数：把直觉变成显式权衡

第二十章第 75 行给了状态选型的形式化表达：

```text
state_cost = latency_weight × L + coupling_weight × K + storage_weight × S
```

- `L`：延迟成本（共享卷最低，消息+artifact 最高）
- `K`：耦合成本（共享卷最高，消息最低）
- `S`：存储成本（快照派生的共享基线最省，消息+artifact 的对象存储要看留存策略）

**这个函数的意义不在算出数字，而在强迫显式化**。三个例子：

- 实时协同编辑（多人共改一份文档）：latency_weight 高，接受 coupling——共享卷/共享内存合理；
- 合规评测平台：coupling_weight 高（耦合=风险），latency 无所谓——消息+artifact 必选；
- 并行探索五条方案：每条独立、最后择优——快照派生 + 选择式合并，成本最低。

**企业评审的问法**：不问"用哪个模型"，问"这三个权重业务方怎么定"。权重定不出来，说明需求还没想清楚。

### 2.5 三个模型与四个通道的配对关系（引申）

通信和状态不是独立决策，它们有自然的配对：

| 状态模型 | 自然配对的通道 | 理由 |
|---|---|---|
| 共享卷 | （本卷内直接读写，通信退化为文件操作） | 状态即通信——最快，但审计全靠文件系统 |
| 快照派生 | 出口网关 / 消息 | worker 各自独立，交互是任务分发与结果提交，消息最配 |
| 消息+artifact | 消息传递 | 同一个范式的两面：说话用消息，记忆用 artifact |

注意一个结构性观察：**共享卷把"说话"和"记忆"合并了**（写文件就是通信），这是它快的根源，也是它危险的根源——**通信的不可审计与状态的弱契约是同一枚硬币的两面**。而消息+artifact 把两者分开又同时显式化，这是它慢的根源，也是它可审计的根源。

## 第三部分：两个完整场景走一遍（决策演练）

### 场景 A：三路并行的数据分析（来自策略复盘工作流）

任务：效果估算、稳健性检验、归因分析三路并行，最后汇总报告。

- **通信**：三路 worker 由 orchestrator 创建、任务经消息下发（或工作流引擎的节点调用）；worker 之间**没有直接通信需求**——通道选型的第一问永远是"谁和谁真的需要说话"；
- **状态**：输入数据用 artifact 引用分发（同一份数据，哈希寻址）；每路输出结构化结果（不是文件系统改动），汇总节点消费三份结果生成报告；
- **合并**：无合并问题——三路输出是结构化字段而非工作区改动，汇总是"拼接"不是"融合"；
- **教训对照**：语料里 A 类故障（Agent 自行缩小任务范围）就是"任务要求存在于提示词而非消息契约里"的代价——状态外置到代码后，这类漂移被结构性消除。

### 场景 B：多 Agent 协作修复一个仓库（Coding 场景）

任务：三个 Agent 分别负责定位、修复、验证，工作区共享。

- **通信**：任务分派走消息；但三路需要共享仓库状态——**这里共享卷有真实吸引力**（克隆三份仓库再合并是重量级操作）；
- **状态**：若用共享卷，五条纪律全上（目录所有权：定位 Agent 只读，修复 Agent 写 src，验证 Agent 只读 + 写 reports；原子写入：补丁先写临时文件再 rename）；若安全要求高，改为快照派生——各改各的副本，orchestrator 做 git merge 式合并；
- **失败传播预演**（为第三十二章埋线）：验证 Agent 失败时，修复 Agent 的产出要不要作废？——依赖图决定：验证依赖修复，修复不依赖验证；部分成功语义：保留修复产出，只重跑验证；
- **决策启示**：同一个场景，"团队内互信 + 效率优先"选共享卷（配纪律），"不可信代码 + 审计优先"选快照派生——**威胁模型决定状态模型，这是第十章的逻辑在状态层的重演**。

## 企业视角

**给平台团队**：通信与状态选型决定了审计的粒度上限。选了共享卷，事后取证只能靠文件系统日志和进程痕迹；选了消息+artifact，每次交互天然是记录。合规要求高的业务，应该在架构评审阶段就锁定向右的选项。

**给安全团队**：三个高危点——vsock 暴露给租户（宿主攻击面）、共享卷的恶意污染（隔离边界自凿）、IP 鉴权（身份误用）。checklist 化之后都是可检查项。

**给成本团队**：共享卷的锁竞争和存储压力、快照派生的合并人工成本、消息+artifact 的对象存储留存费用——三种模型的成本形态完全不同，第十一章的账本方法要按模型分列。

## 本章小结

| 关键认知 | 一句话 |
|---|---|
| 隐藏排序线 | 所有选项排在"快而隐式 → 慢而明确"的谱上，越明确越可审计 |
| vsock | host↔guest 的血管，不是 VM↔VM 的网络；暴露给租户 = 扩大宿主攻击面 |
| 五字段身份包 | 任务树、发送者、接收者、过期时间、幂等键——跨沙箱请求的最小身份 |
| 共享卷五纪律 | 目录所有权、原子写入、版本标记、锁、只读挂载——快但危险，纪律换安全 |
| 消息两条纪律 | artifact 引用不塞本体；消息送达不等于文件一致，哈希寻址补上 |
| 状态三模型 | 写入在哪，一致性责任就在哪：卷靠纪律、快照靠合并、消息靠契约 |
| 合并红线 | 合并冲突必须 orchestrator 层解决——合并是业务逻辑，不是基础设施能力 |
| 配对结构 | 共享卷把通信与记忆合一（快而不可审计），消息+artifact 分开且都显式（慢而可审计） |

## 思考题（能算账的那种）

1. 一个三路并行任务，单路平均执行 40 秒。方案一共享卷：无分发延迟，但存在 10% 概率的锁冲突（每次冲突损失 30 秒）；方案二消息+artifact：每路增加 3 秒分发与提交延迟，无冲突。按期望时间比较两方案，并说明什么业务条件下你的选择会反转。
2. 为场景 B（三 Agent 协作修仓库）设计五字段身份包的具体字段值，并指出其中哪个字段在"验证 Agent 失败重跑"时必须改变、哪个必须保持不变。
3. 共享卷上 worker A 需要向 worker B 交付一个 5GB 的中间数据集。设计原子交付流程（临时文件、rename、版本标记、哈希校验各在哪一步），并说明为什么 `rename` 是 POSIX 原子操作而"写完文件"不是。
