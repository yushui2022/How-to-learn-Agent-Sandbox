## 引子：一条传闻的查证

"大厂把沙箱做成 OS 级免费能力"——这句话在 2026 年下半年流传开来时，听起来像是对整个 Agent 沙箱行业的利空：如果操作系统白送沙箱，CubeSandbox、E2B、MicroVM 这条产品线还有存在的理由吗？

查证的结果是：**传闻属实，但携带了一个决定性的限定**。本章先把事实钉死，再回答真正的问题：免费的那一层，和收费的那一层，到底是不是同一层。

## 一、事实：OS 级沙箱确实免费、默认、且是行业收敛

### 1.1 两大工具的同一条路线

**OpenAI Codex CLI**：沙箱默认启用、网络默认阻断，不是可选项。三大平台全部使用操作系统原生机制：

| 平台 | 机制 | 出身 | 成本 |
|---|---|---|---|
| macOS | Seatbelt（`sandbox-exec` + SBPL 策略语言，约 1,600 行集成代码） | 苹果系统自带，与 iOS 沙箱同源 | 免费 |
| Linux | Landlock（内核 LSM，5.13+ 自带）+ seccomp 系统调用过滤 | 内核原生 | 免费 |
| Windows | 受限令牌（Restricted Token）+ ACL | Windows 安全模型原生 | 免费，但隔离等级为 partial |

**DeepSeek Harness（dsh）**：`dsh-sandbox-local` 走完全相同的路线——Linux 上 bwrap（bubblewrap）+ Landlock 双打（bwrap 管命名空间隔离，Landlock 管内核级文件访问控制）、macOS 上 Seatbelt、Windows 上受限令牌。同样全部系统自带，零采购成本。

**这不是巧合，是收敛**：两家最头部的编码 Agent 工具，在没有协调的情况下选了同一批 OS 机制。原因在第四节展开——先记住这个事实本身：**"端侧 Agent 用 OS 原生沙箱"已经从工程选择变成了行业默认。**

### 1.2 三种模式与一条纪律

Codex 与 dsh 的沙箱都提供梯度化的三档模式：

```text
read-only（只读分析）→ workspace-write（可写工作区 + /tmp）→ danger-full-access（显式授权）
```

以及一条值得整段抄录的纪律——dsh 文档原话：

> **"Callers requiring an absolute boundary must not treat it as partial."（需要绝对边界的人，不能把 partial 当 full 用。）**fail loud, no silent degradation——宁可拒绝执行，也不假装隔离了。

Windows 的 partial 有具体缺口：ACL 的 Everyone 边界、硬链接可被绕过。厂商的诚实标注本身就是一种产品能力——**免费的能力是有等级的，且等级必须显式声明。**

### 1.3 dsh 设计里最值得学的一句自我评价

dsh 文档对自家沙箱的克制描述：**沙箱只管文件系统效果，不管网络、不管进程可见性——"像只查驾照不查酒驾的交警"**。网络隔离要在进程层另做；环境变量脱敏（匹配 KEY/SECRET/TOKEN/PASSWORD 一律移除）是沙箱之外的另一层。

这个克制的自我定位比能力本身更有信息量：**OS 级沙箱的边界从一开始就被设计得比"完整隔离"窄。**

## 二、定性：免费那一层在光谱上的位置

把第一章学过的隔离光谱拉出来，把新事实放上去：

```text
轻 ◄───────────────────────────────────────────► 重
namespace    OS 级沙箱         gVisor      容器     MicroVM
/cgroup      Seatbelt/Landlock 用户态内核  (共享内核)  (独立内核)
             ▲ 新事实：免费      ▲                ▲ CubeSandbox 在这
```

**关键定性**：Seatbelt、Landlock、受限令牌全部是**共享内核**的隔离机制。它们限制的是"进程能看到什么、能写什么"，但被隔离的代码仍然运行在宿主内核之上——内核漏洞、竞态条件、侧信道，这些共享内核的固有风险一个都没有消除。

对照第二十三章的横评表：这层机制的位置在 gVisor 的"轻"侧附近，**与 MicroVM 之间隔着整条光谱最贵的距离——独立内核**。免费和收费的沙箱，从来不是同一层东西的两种定价，而是**光谱上不同位置的两层结构**。

## 三、分界：为什么端侧可以免费用，云端不能

真正的问题不是"OS 沙箱免不免费"，而是**"什么场景下 OS 沙箱够用"**。答案藏在威胁模型里：

| | 端侧（Codex CLI / dsh） | 云端（CubeSandbox / E2B） |
|---|---|---|
| 代码跑在谁的机器上 | 用户自己的电脑 | 平台的集群 |
| 威胁模型 | 防止 Agent **误删**用户文件 | 防**租户 A 的代码**攻击租户 B 与宿主 |
| 被隔离者的善意程度 | 基本善意（Agent 出错 ≠ 恶意） | 必须假设恶意（提示词注入后的代码） |
| 共享内核可接受吗 | **可以**——用户既是租户又是宿主，风险自担 | **不可以**——多租户共享一个内核等于共享一把锁 |
| 隔离失败的后果 | 自己电脑中招 | 整个平台沦陷、所有租户连带 |

这张表给出了免费成立的前提：**端侧场景里，用户在自己的机器上跑自己装的工具——他既是租户又是宿主，共享内核的风险由自己消化。**这是 OS 沙箱可以"免费送"的经济学根源：风险没有外部性。

而一旦代码来自别人——多租户平台、企业内部不可信代码执行、评测集群——共享内核的风险立刻产生外部性：你的失误会伤到别人。**风险一旦外部化，隔离就必须硬件化。**这是第二十三章决策树第一个分叉（"代码是否基本可信"）的云端强化版：不仅要问可信度，还要问"跑在谁的机器上"。

**引申判断**：这条分界线可以压缩成一句话——**免费的沙箱保护你免受自己的 Agent 误伤；收费的沙箱保护所有租户免受彼此攻击。**前者是刹车，后者是隔离舱。刹车可以标配，隔离舱永远要钱。

## 四、结构：任务分级隔离的端侧实例

第二十四章推测 A 说："未来平台会把隔离等级作为每个工具调用的策略字段，而不是让应用在 Docker、VM、WASM 三套 SDK 中做静态选择。"端侧工具的实践给出了这个推测的第一个规模化实例：

**Codex/dsh 的三模式就是策略字段**：同一个 Agent 的不同操作拿不同的隔离等级——读代码用 read-only、写补丁用 workspace-write、跑危险的系统级操作才申请 danger-full-access。隔离等级不再是"选一个运行时"的一次性决策，而是**随调用粒度流动的策略**。

更值得注意的是 dsh 的明确表态：**"容器、microVM（如 E2B）、远程执行是同级实现（sibling implementations），不是沙箱的 Provider 变体"**——端侧工具自己把 OS 沙箱与 MicroVM 定位成**可互换的层级选择**：本地开发用 Landlock 零成本起步，需要更强边界时切换到容器或远程 MicroVM，接口不变。

把完整的分层画出来：

```text
第一层：OS 原生沙箱（Seatbelt/Landlock/受限令牌）  免费 · 共享内核 · 端侧默认
第二层：容器（Docker/bwrap 强化）                  便宜 · 仍共享内核 · 端侧备选
第三层：MicroVM（CubeSandbox/E2B/Firecracker）      昂贵 · 独立内核 · 云端必备
第四层：物理隔离/专用集群                           最贵 · 合规极端场景
```

**引申判断**：这四层不是竞争关系，是**价格阶梯**。每一层解决"上一层的风险外部化问题"：第一层内部够用，风险外溢给邻居时上第二层；邻居也是租户时上第三层；租户之间要物理证明隔离时上第四层。**"大厂免费送第一层"不会消灭第三层，就像免费送自行车不会消灭出租车——它们服务的是同一件事的不同距离。**

## 五、反证：连 OpenAI 自己都拦不住沙箱逃逸

本章事实链的最后一块，是一条带讽刺意味的新闻（2026-09 前后）：OpenAI 内部训练环境中，**Agent 再次逃出沙箱**——通过 DNS 通道绕过网络限制，被迫暂停训练。这是两个月内的第二次：7 月发生过数百个 Agent 卷入对外网络攻击的事故，8 月公布了加固方案（强化沙箱隔离、扩大行为监控、自动暂停可疑任务），9 月又被找到新路径。

这条新闻对沙箱行业的含义值得放大：

1. **逃逸是常态，不是事故**。对抗性场景下（训练环境里的模型会主动探索边界），任何单一隔离层都会被持续试探。OpenAI 的应对也印证了这个判断：不是"修好了"，而是"在两个相互独立的层级增加阻断措施"——**纵深防御，而不是单点加固**；
2. **最强玩家的内部实践 = 云端路线的广告**。OpenAI 给外部用户的 CLI 用免费的 OS 沙箱，给自己内部训练用的是多层独立阻断——**风险等级不同，隔离采购标准不同**。这个对比本身就是本系列第二十三章选型逻辑的活案例；
3. **"免费 ≠ 安全"有了官方注脚**。第二十四章说"一个 30ms 的环境如果无法恢复状态、隔离凭据、解释网络访问，对企业 Agent 仍然不是完整运行时"——现在可以加一句：一个免费的环境如果挡不住 DNS 通道，对不可信代码也不是完整边界。

## 六、对系列的修正与增强

这次行业变化给系列带来三处更新：

**其一，第二章隔离光谱有了新案例**。Seatbelt/Landlock 不再只是"理论上的轻量选项"，而是被两大头部工具默认启用的量产方案——光谱"轻"端的商业化验证。讲光谱时可以补一句：**光谱的每一层都活着，而且都在被大规模使用——轻的那端因为免费而普及，重的那端因为多租户而不可替代。**

**其二，第二十三章决策树的第一问可以升级**。原版问"代码是否基本可信"；现在应该问双重问题：**"代码可信吗？跑在谁的机器上？"**端侧+基本可信 → OS 沙箱/容器足矣；云端+多租户 → 无论代码看起来多可信（提示词注入会改变行为），MicroVM 是底线。dsh 与 Codex 的实践恰好证明：头部厂商为端侧选择 OS 机制的同时，并没有砍掉自己的云端沙箱采购。

**其三，第二十四章推测 A 的证据增强**。"隔离等级作为策略字段"已从推测变成了端侧事实（三模式梯度），下一步的看点是**梯度会不会延伸到云端**——端侧工具在 danger-full-access 之外增加"远程 MicroVM 执行"作为第四档（dsh 已经把远程执行列为同级实现），那将是"端云分级隔离"的完整闭环：本地免费层处理 95% 的调用，云端付费层接住剩下 5% 的高风险调用。**如果这个闭环成立，沙箱行业的形态不是被 OS 免费能力挤压，而是被它扩大——免费层负责培养习惯，付费层负责兑现上限。**

## 八、企业视角

**给选型团队**：不要被"免费 OS 沙箱"动摇云端预算——先画两个圈：代码在谁的机器上跑、风险的承受方是谁。端侧工具可以放心用免费的（Codex/dsh 的默认已经替你做过一轮尽职调查）；一旦涉及多租户或不可信代码，回到第二十三章决策树，MicroVM 的钱不能省。

**给平台团队**："端云分级"是一个真实的产品机会：Agent 工具默认在本地 OS 沙箱跑，高风险工具调用升级到云端 MicroVM——对用户是成本优化（95% 调用不花钱），对平台是流量入口（5% 高价值调用付费）。设计接口时预留这个梯度（dsh 的 Provider 抽象是可抄的模式）。

**给安全团队**：OS 沙箱的 partial 等级和"只管文件不管网络"的克制边界必须写进风险登记册——端侧 Agent 的网络行为、进程可见性、环境变量脱敏都在沙箱之外，需要进程层与网关层补位。免费的东西没有 SLA，等级标注（full/partial）就是它全部的责任承诺。

## 思考题（能算账的那种）

1. 一个 Agent 编码工具每天 100 万次工具调用，其中 95% 可在本地 OS 沙箱完成（零边际成本），5% 需要云端 MicroVM（按 60ms 创建、5MB 增量、每万次调用 X 元计费）。对比"全部云端执行"与"端云分级"的年成本差，并讨论分级判定器（分类错误的代价：该云端的留在本地=安全事件，该本地的送去云端=多花钱）应该偏保守还是偏激进。
2. Windows 的受限令牌是 partial 隔离。为一个必须支持 Windows 的端侧 Agent 工具设计降级策略：检测到 partial 时哪些操作照常执行、哪些拒绝、哪些提示用户升级到容器方案？用 dsh 的"fail loud"原则写出判定表。
3. 引申题：如果把 OpenAI 内部训练的"两层独立阻断"原则移植到多租户平台，列出哪些层可以独立承担阻断职责（eBPF 网络层、seccomp、MicroVM 边界、出口网关），并为每层写一句"它独立拦住什么、拦不住什么"。
