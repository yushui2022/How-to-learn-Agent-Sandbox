## 引子：一行环境变量到底值多少钱

一个团队已经用 E2B SDK 写了 2,000 行 Agent 代码：创建沙箱、写文件、运行代码、读取结果、上传 artifact。现在他们想把执行底座迁到自建集群，理由可能是数据合规、成本或区域可用性。理想答案是改一行 `E2B_API_URL`；现实答案通常是先遇到一串差异：创建请求返回字段不同，超时语义不同，命令输出是流还是最终字符串，文件路径是否持久，销毁后 artifact 是否还可读。

这说明“兼容”有两个层次：

* **语法兼容**：客户端能发出同样的 HTTP/SDK 调用。
* **语义兼容**：相同调用在边界条件下产生足够接近的状态、错误、时序和安全行为。

第一层能让 demo 跑起来，第二层才决定企业迁移是否可控。E2B 接口之所以有生态价值，不是因为它规定了唯一的虚拟化技术，而是它把 Agent 最常用的沙箱动作收敛为一组可复用的“最小语言”。

## 一、沙箱接口的最小语言

### 1. 生命周期

Agent 应用首先需要一个可寻址的执行环境：创建、查询、暂停或终止。CubeSandbox 的 E2B-compatible 示例提供了 `POST /sandboxes` 和 `DELETE /sandboxes/{sandboxID}`，请求体中的 `templateID` 指向预先准备的模板；示例客户端把响应解析为 `sandboxID`、`templateID`、`clientID`。这是真实仓库代码事实，不等于完整 E2B API 的全部字段。

生命周期接口至少要回答四个问题：

1. 创建请求重复提交时，是返回原实例还是再建一个？
2. 连接断开后，实例是继续运行、进入宽限期，还是立即回收？
3. `delete` 返回成功时，文件卷、日志和凭据是否已经完成清理？
4. 客户端查询到的状态是控制面状态，还是节点执行层确认后的状态？

若这些问题没有写进兼容契约，表面相同的 `create()` 会在故障重试时产生不同结果。建议所有创建动作携带业务侧 `idempotency_key`，并在响应中返回服务端生成的稳定 `sandbox_id`。不要把 `clientID` 误当成租户身份或安全凭据；字段的安全含义必须从服务端鉴权设计中单独定义。

### 2. 执行与文件

Agent 的最小执行面通常包含三类操作：

```text
run_code(language, source, timeout)
run_cmd(command, cwd, env, timeout)
files.write/read/list(path)
```

`run_code` 适合把短片段交给语言运行时，`run_cmd` 适合编译、测试和系统工具；文件操作承载跨轮状态。接口设计时不要把两者混成“任意字符串执行”：语言运行时、shell、解释器和工作目录分别有不同的超时、输出和策略。

文件语义尤其容易产生假兼容：路径是否相对于工作目录？写入是否原子？大文件是同步传输还是返回对象引用？删除沙箱后 artifact 是否保留？E2B SDK 的文件与代码执行抽象降低了上层接入门槛，但自建兼容层要把这些行为逐项写成测试，而不是只做端点名称映射。

### 3. 输出、流和 artifact

Agent 需要的不是“HTTP 200”，而是可判断下一步的证据。一个最小结果结构可包含：退出码、终止原因、stdout/stderr 引用、生成文件列表和计费/审计 ID。流式输出与最终输出也要区分：

```text
stream：适合交互反馈，可能断线，必须有序列号和重连点
final：适合重试与审计，必须有明确完成标记
artifact：适合大文件，引用应有大小、哈希、媒体类型和过期时间
```

如果兼容层只返回最后 4 KB 的 stderr，许多编译失败仍能显示给模型，却无法满足企业取证；如果把数百 MB 日志全部回填上下文，成本与提示词注入风险会同时上升。语义兼容要规定截断方式、编码、最大输出和 artifact 的生命周期。

## 二、`E2B_API_URL` 背后的协议翻译

CubeSandbox 示例客户端从环境变量读取 `E2B_API_URL` 和 `E2B_API_KEY`，向该地址发送带 `Authorization: Bearer ...` 的请求。这个设计把“客户端使用哪个服务”从业务代码中抽出来：同一程序可指向托管地址、测试环境或自建 Cube API。它的价值在于减少迁移触点，而不是保证所有服务行为一致。

一个兼容网关通常要做四步翻译：

1. **鉴权翻译**：把 SDK 的 bearer token 映射为平台租户、项目和权限；不能为了兼容而接受任意 token。仓库示例注明禁用鉴权时可使用任意非空 key，那是本地开发便利，不能复制到生产。
2. **模板翻译**：把 E2B template 语义映射到 CubeSandbox 模板或镜像版本，并明确架构、内核和工具链差异。模板 ID 相同不代表包版本相同。
3. **生命周期翻译**：把创建、暂停、恢复、销毁映射到控制面状态机；若底层只支持创建/删除，应明确返回“未支持”而不是静默模拟。
4. **错误翻译**：把 HTTP 状态、平台 reason code 和执行错误分层。`404` 可能是 sandbox 不存在，也可能是租户无权看见；兼容层应避免泄露资源存在性。

可以用一个“兼容预算”检查迁移范围：

```text
迁移改动量 ≈ Σ（调用类型 i 的使用点数量 × 行为差异权重_i）
```

这是规划模型，权重需要由真实代码审计得到。若团队只使用创建、命令、文件三类动作，迁移改动量可能很小；若依赖实时流、浏览器 CDP、暂停恢复和高级网络策略，兼容层缺口会迅速放大。

## 三、事实标准为何会形成

### 1. 接口先于底座

Agent 框架要把“执行代码”接到模型循环中，最小需求高度相似：获得一个环境、运行代码、读写文件、收集结果、销毁环境。接口一旦覆盖这些高频动作，上层框架、教程和示例就会围绕它累积。底层可以是托管 MicroVM、Kata、gVisor 或其他运行时，应用先依赖的是动作模型。

这和数据库的 SQL、对象存储的 S3 兼容有相似之处：接口成为迁移语言，服务商在实现和运维上竞争。类比有边界——沙箱的网络、凭据和生命周期远比 SQL 查询依赖运行环境，不能把“兼容 API”理解为完全可替换。

### 2. 迁移成本的复利

企业选择接口时，可以把切换成本拆成：

```text
C_switch = C_code + C_behavior + C_data + C_operation + C_compliance
```

`C_code` 是调用点改造；`C_behavior` 是超时、流、错误和状态差异测试；`C_data` 是模板、artifact 和持久卷迁移；`C_operation` 是监控、告警、容量和值班体系；`C_compliance` 是审计、留存和数据出境重做。公开产品常强调 SDK 兼容能降低 `C_code`，但企业项目最容易低估后三项。

接口兼容的经济价值来自存量：当一套 SDK 已被多个 Agent、内部模板和供应商集成，切换底座不会重写全部业务逻辑。兼容者得到生态入口，原服务商则不能只靠私有 API 锁住用户；双方的竞争从“谁有最酷的虚拟机”转向“谁能在相同动作下提供更可靠的语义”。

## 四、诚实兼容清单

兼容项目最危险的宣传句是“完全兼容”。更可靠的做法是公开三张表：

| 能力 | 可兼容的表面 | 需要单独验证的语义 |
|---|---|---|
| 创建/销毁 | 端点、SDK 方法、ID 格式 | 幂等、TTL、销毁完成、数据留存 |
| 命令/代码执行 | 参数名、退出码、超时字段 | shell、环境变量、信号、流式输出 |
| 文件 | read/write/list 方法 | 原子性、大文件、权限、artifact 保留 |
| 模板 | template ID 概念 | 包版本、CPU 架构、内核、网络工具 |
| 网络 | 代理或出口配置 | DNS、白名单、凭据、审计与延迟 |
| 暂停/恢复 | 方法名或状态 | 内存快照、后台连接、恢复时延、失败回滚 |

例如，CubeSandbox 仓库的最小 Go 示例只覆盖创建和删除，并设置 HTTP 客户端 30 秒超时。它证明的是兼容入口可用，不证明仓库示例已经实现 E2B SDK 的全部文件、进程、流或暂停语义。写迁移指南时应把“仓库已覆盖”“适配层已覆盖”“尚未实现”分开列出。

兼容测试也要按故障设计，而不是只测 happy path：创建请求超时后重试、执行过程中客户端断开、artifact 上传一半、节点故障后查询状态、删除与日志读取并发、租户无权限访问别人的 sandbox。每个场景都应记录期望状态和可重放证据。

## 五、横向参照：E2B、Kubernetes Agent Sandbox 与自建底座

**E2B** 的优势是托管体验和 SDK 生态：开发者按公开 API 创建环境、执行代码和管理文件，基础设施细节由服务方承担。其代价是供应商策略、区域、配额、数据驻留和价格受服务条款影响；本文不对闭源实现做安全推断。

**Kubernetes Agent Sandbox** 的方向是把 Agent 沙箱建模为 Kubernetes 可编排资源，利用 CRD、调度、配额、节点池和控制器管理长生命周期会话。它解决了“如何进入企业 K8s 运维体系”的问题，但不自动解决 E2B 语义兼容，也不替代沙箱运行时的硬件隔离、网络出口和凭据治理。

**CubeSandbox** 走的是自建 MicroVM + E2B-compatible API 路线。其价值包括控制数据面、定制模板和把已有 E2B 客户端作为迁移入口；代价是团队要承担 KVM、网络、快照、容量、升级和故障响应。兼容 API 只能减少应用层迁移工作，不能消除基础设施运营责任。

## 六、企业视角：押注生态还是绑定私有接口

决策时可以画两条轴：接口迁移能力和底座运营能力。已有 K8s、合规要求高且有基础设施团队的企业，可能愿意使用兼容层换取控制权；需要快速上线、区域覆盖和托管值班的团队，更关心供应商的服务边界。两者都不是技术优劣排序。

合同与架构评审至少应问：

* API 版本和弃用通知期多长？是否有兼容性测试套件？
* 模板、artifact、日志和审计数据如何导出？删除后多久完成？
* 网络、凭据和租户配额的语义是否能在自建/托管间保持？
* 服务限额、重试建议和故障状态是否公开？
* 迁移演练能否在不修改 Agent 业务逻辑的情况下切换 endpoint，并验证行为差异？

真正可持续的生态位不是“永远兼容所有功能”，而是稳定最小核心、明确扩展字段、为差异提供能力探测和版本协商。例如客户端可以先查询 `capabilities`，再决定是否使用 pause、流式输出或浏览器会话；不支持的能力应返回结构化错误，而不是假装成功。

## 本章小结

E2B 接口的生态价值来自动作模型的收敛：生命周期、执行、文件和结果是大多数 Agent 的共同语言。`E2B_API_URL` 能降低代码迁移触点，但语义兼容必须覆盖幂等、超时、状态、输出、artifact、网络和删除证明。CubeSandbox 的 v0.7.2 示例验证了 E2B-compatible REST 入口与创建/删除路径，不能被扩大解释为完整 SDK 兼容。企业选择时应把代码改造、行为验证、数据迁移、运营责任和合规重建一起计入迁移成本。

## 思考题（能算账的那种）

1. 某 Agent 有 120 个 `create/run/files/delete` 调用点。假设 70% 只用核心语义、20% 依赖流式输出、10% 依赖暂停恢复，为三类调用设置 1、3、8 的差异权重，计算一个迁移改动指数，并说明权重如何由故障测试校准。
2. 兼容层声称“支持创建与删除”。设计 5 个删除相关故障场景，分别列出 sandbox 状态、卷状态、日志状态和客户端可见响应，找出哪些场景需要异步 operation ID。
3. 一个企业每月生成 10 TB artifact，托管服务保留 7 天，自建平台保留 30 天。设存储单价和下载单价为变量，写出两种方案的成本差异，并把合规留存与导出能力作为非价格约束加入决策。
