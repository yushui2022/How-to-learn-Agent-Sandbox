## 引子：一张账单不等于一张状态机

一条沙箱账单可能写着：12:00 创建，12:01 运行，12:10 暂停，13:00 恢复，13:05 迁移，13:06 销毁。运营真正需要知道的是：13:05 的“迁移”是否已经是 CubeSandbox 的真实状态？暂停期间是否还占内存？删除一个暂停沙箱是否必须先唤醒？超时和用户主动 kill 是否产生同样的审计证据？

生命周期语义的难点在于，产品需要一张完整的设计模型，而实现只承诺有限的状态枚举和合法转换。把设计状态直接当成 API 返回值，会导致客户端等待不存在的状态；把瞬时状态隐藏，又会让并发请求和重试失去依据。

## 一、先区分三张图

### 设计状态图

为了讨论完整运营语义，可以使用：

```text
Created → Running → Pausing → Paused → Resuming → Running
   │         │          │         │          │
   └─────────┴──────────┴─────────┴──────────┴→ Destroyed

Running → Migrating → Running
```

这是架构模型，不代表每个节点都有公开枚举。`Migrating` 表示并发架构里的排水和重新放置过程，当前 `v0.7.2` 文档没有把它列为用户可见状态；迁移可能通过暂停快照、节点重建和控制面绑定完成。

### 对外 API 状态

CubeSandbox 生命周期文档列出的稳定/瞬时状态是 `running`、`pausing`、`paused`、`resuming`、`terminated`。创建中的内部阶段、节点选择和销毁清理可能不直接暴露。客户端应以文档和 protobuf/SDK 类型为准，未知状态采用“不可执行、重新查询”的保守策略，而不是猜测。

### 资源状态

“状态”至少有三条正交轴：

```text
API 状态：running / paused / terminated
资源状态：CPU/内存驻留、快照、卷引用、网络绑定
任务状态：idle / executing / waiting / failed
```

一个 `running` 沙箱可以没有正在执行的任务，一个 `paused` 沙箱仍有快照和存储引用，一个 `terminated` 任务可能还有审计归档。把三条轴压成一个字符串，是很多清理和计费 bug 的来源。

## 二、合法转换与幂等

| 当前状态 | 事件 | 目标 | 关键条件 |
|---|---|---|---|
| Created/内部创建中 | create 成功 | Running | 节点、镜像、网络和 agent 就绪 |
| Running | 超时 + pause | Pausing→Paused | 快照与元数据绑定成功 |
| Running | 超时 + kill | Terminated | 任务终止、卷和网络清理 |
| Paused | connect/resume | Resuming→Running | 快照可读、节点准入、代理可恢复 |
| Running/Paused | kill/delete | Terminated | 清理完成后才返回成功 |
| 任意瞬时态 | 重复操作 | 原操作结果或 409/503 | 不得并行启动第二个动作 |

CubeMaster 的 pause 实现会先创建快照绑定，再调用 Cubelet `Update(pause)`；成功后写入 READY，失败则记录 FAILED。对 RPC 超时这一特殊情况，Cubelet 可能已经 PAUSED，Resume 路径会探测并尝试修复绑定；明确的 Cubelet 失败则不能假设快照可恢复。源码见 [sandbox_resume_pause.go](https://github.com/TencentCloud/CubeSandbox/blob/f1aaa737fb3862202b1731e0e0d844c28779f930/CubeMaster/pkg/service/sandbox/sandbox_resume_pause.go)。

这类语义要求每次操作带 `request_id`/幂等键：客户端超时重试时，控制面应查询已有操作状态，而不是再次创建快照。状态写入顺序也要明确，避免“运行时已暂停、数据库仍记录 Running”导致 sweeper 重复暂停。

## 三、TTL、keep-alive 与 idle 的三个时间

### 生命周期 TTL

TTL 是沙箱从创建或某个保留点开始最多存在多久，回答“无论是否活跃，何时必须结束”。它服务于成本、合规和故障回收。CubeSandbox 的 `timeout` 主要描述空闲超时，不能自动当作绝对 TTL；若企业需要硬上限，应在控制面另设 `max_age`。

### 空闲超时

空闲回答“多久没有可观测活动”。CubeSandbox sweeper 使用最近活动时间和创建时间的较新者作为基线，并支持 `NEVER_TIMEOUT`。它不是 CPU 为零检测：等待中的网络连接、SDK 心跳、API 调用和代理请求是否算活动，要由平台定义并测试。错误的定义会让正在运行的任务被暂停，或让永远 idle 的沙箱持续占用资源。

### Keep-alive

Keep-alive 是客户端续期意图，可以刷新截止时间，但不能让不可信任务无限延长资源占用。建议区分：用户交互心跳、任务执行心跳、控制面内部探活，并对每种心跳设置租户级上限。来自沙箱内进程的自发 HTTP 请求不应自动续租，否则模型可以通过循环请求阻止回收。

## 四、空闲判定的证据与误判代价

可以定义一个保守的活动信号集合：

```text
active = API_request ∨ tool_exec ∨ guest_process_in_progress
         ∨ policy_authorized_egress ∨ explicit_keepalive
```

但每个信号都有成本：

- `API_request` 容易观察，却可能只是客户端轮询；
- `tool_exec` 能反映 Agent 工作，但需要编排器上报；
- `guest_process_in_progress` 需要 guest agent，且可能被任务伪造；
- `authorized_egress` 能证明有网络活动，却看不见纯 CPU 任务；
- `keepalive` 最容易实现，也最容易被滥用。

因此，暂停决策应带“最后活动来源”和时间戳，便于解释为何触发。对长编译和数据分析任务，可以在任务开始时申请一个带上限的 execution lease，而不是把所有低 CPU 阶段视为空闲。

## 五、超时、优雅退出与产物抢救

销毁不是发送一个 `kill -9` 就结束。对仍在执行的任务，建议采用宽限阶梯：

```text
通知任务即将终止
  → 停止接受新 tool call
  → SIGTERM/任务取消
  → 等待 grace period
  → 采集 stdout/stderr、退出码、关键 artifact
  → SIGKILL 未退出进程
  → 卸载网络、卷和 cgroup
  → 删除快照与临时层
  → 写入 terminated + cleanup receipt
```

CubeSandbox 的具体 SDK/API 行为以版本文档为准；上图是生命周期设计模型。产物抢救必须有大小和时间上限，不能因为“先上传全部目录”而让超时任务无限延长。对失败任务，记录清理动作和未能收集的证据，比把状态伪装成成功更可靠。

## 六、销毁语义：删除请求成功意味着什么

合规要求通常不是“数据库里没有一行记录”，而是证明沙箱可访问的数据路径已经关闭：运行进程、cgroup、TAP/vsock、临时文件、COW 层、快照对象、插件卷引用和审计索引都完成处理或进入明确的保留状态。

`v0.7.2` 生命周期文档说明，删除暂停沙箱时可以直接删除 paused tombstone、pause 快照和 CoW 资源，不必先 Resume；成功返回 `204 No Content` 表示清理完成，生命周期事件不会伪造一次 resumed。若另一个 pause/resume/delete 操作持有锁，接口可能返回 `503` 并带 `Retry-After: 2`，客户端应等待后重试。参考：[lifecycle.md](https://github.com/TencentCloud/CubeSandbox/blob/f1aaa737fb3862202b1731e0e0d844c28779f930/docs/zh/guide/lifecycle.md)。

销毁凭证（cleanup receipt）至少记录：sandbox ID、快照/卷 ID、节点、开始/结束时间、清理步骤结果、失败项与重试建议。对远端对象存储的快照，逻辑删除和物理回收可能分离，合规报告要分别说明“不可访问时间”和“物理删除完成时间”。

## 七、迁移与故障域：设计模型中的 Migrating

当节点排水、维护或故障时，平台可能要把沙箱迁移到另一节点。若状态是可恢复的快照，迁移可以建模为 `Running→Pausing→Paused→Resuming→Running`，而不是新增公开 `Migrating` 枚举。迁移期间要处理：

- 快照与 COW 层的复制一致性；
- plugin volume 的引用计数；
- 原节点网络连接和端口释放；
- 新节点容量准入；
- trace_id、任务重试和结果幂等。

如果迁移失败，不能自动把原状态标成 Destroyed；应区分“原沙箱仍可恢复”“快照已完成但新节点准入失败”“两端都不可用”。这也是第十八、十九章故障域和容量规划的接口。

## 八、横向参照：E2B、Kubernetes 与 Serverless

E2B 的沙箱 API 以连接、运行、暂停/恢复和 TTL 为核心，开发者体验统一；其具体托管上限、计费和状态持久化需按官方文档与合同核对。CubeSandbox 自建模式可让企业控制节点、快照后端和网络，但也承担锁、清理、审计和故障恢复责任。

Kubernetes Pod 的 `terminationGracePeriodSeconds` 给出了优雅退出的通用语义，Job TTL 解决完成资源的回收；但 Pod 的 `Pending/Running/Succeeded/Failed` 与 VM 快照的 `Paused/Resuming` 不是一一对应。Agent Sandbox 控制器若把 Pod 作为外层对象、MicroVM 作为内层对象，应在 API 中分别暴露工作负载状态和沙箱资源状态。

Serverless 把调用完成视作执行环境可回收，适合无状态函数；Agent 的状态、文件和多步工具循环要求更细的保留策略。把函数的“请求结束即销毁”套到 Coding Agent，会丢失工作区；把会话永远保留，又失去按需供给的经济性。

## 企业视角：生命周期策略就是成本与合规策略

租户级策略可拆成四组：

```text
保留：max_age / idle_timeout / paused_max_age
交互：keepalive / resume_deadline / retry_budget
清理：grace_period / artifact_window / volume_retention
证明：audit_retention / cleanup_receipt / deletion_scope
```

容量团队关注运行与暂停比例、恢复并发、磁盘水位和清理延迟；安全团队关注快照加密、跨租户引用、删除证明和审计缺口；产品团队关注首个请求 P95、重试次数和用户可感知等待。一个“节省 30% 节点”的策略，如果把恢复 P95 从 300ms 推到 20s，可能并不适合交互式 Agent。

## 本章小结

完整状态机是设计语言，真实 API 枚举是版本契约。CubeSandbox `v0.7.2` 对外重点是 running/pausing/paused/resuming/terminated；Migrating、Created 等可用于架构推演，但不能未经核实写成现有状态。TTL、空闲超时和 keep-alive 必须分开；超时、暂停、迁移、删除都需要幂等、锁、资源清理和可证明的审计结果。

## 思考题

1. 设计一个客户端状态处理器：遇到 `pausing`、`resuming`、`503 Retry-After`、未知状态和请求超时分别做什么？要求不重复创建快照。
2. 某租户要求“暂停最多 24 小时、运行最多 7 天、删除后 30 天保留审计但不得保留数据”。请给出 TTL、paused_max_age、artifact 和审计策略。
3. 节点排水时，100 个沙箱中 20 个 Running、50 个 Paused、30 个 Terminated 清理中。如何安排快照复制、容量准入和故障回滚，避免双重计费和卷引用泄漏？
