## 引子：SWE-bench 的分数，究竟在测什么

一个模型在上个月的仓库环境里解决了 42 个问题，本月只解决了 38 个。模型变差了吗？也可能是依赖版本漂移、系统包变化、测试数据变化，或者某个镜像层在不同节点上没有完全一致。

Agent 评测真正需要的不是“一台能跑代码的机器”，而是一种可以反复出生、暂停、复制、回到同一时刻的环境。Coding Agent 也有同样需求：它在第 20 步把仓库改坏了，最好回到第 15 步继续尝试，而不是从头安装依赖；一个规划器想并行探索五条方案，最好从同一个中间状态派生五个工作空间，而不是重新执行前面的十五步。

CubeSandbox 把这个问题拆成两种状态：**磁盘状态和内存/设备状态**。CubeCoW 用文件系统写时复制管理 rootfs、卷和快照，CubeHypervisor 的快照框架保存 guest 内存与设备状态。二者结合，才得到“快照、克隆、回滚”三种看起来像一个 API、实际上跨越文件系统、内存管理器、VMM 和生命周期状态机的能力。

## 一、先把三个动词分开

| 动作 | 对象 | 身份 | 典型用途 |
|---|---|---|---|
| Snapshot | 当前运行中的沙箱 | 产生一个可复用快照 | checkpoint、模板、暂停、归档 |
| Clone | 当前状态的派生副本 | 产生新的 sandbox_id | 并行 rollout、A/B 实验、批量评测 |
| Rollback | 原沙箱恢复到旧快照 | sandbox_id 不变 | Agent 失败重试、撤销错误步骤 |

这三个动词有三个常见误解：

- **快照不是压缩包。** 它可能由一份 CoW 文件、内存范围文件和设备状态元数据组成，未必把所有数据重新拷贝一遍；
- **克隆不是共享运行时。** 派生时可以共享底层 extent 和文件页，之后每个副本的写入必须相互隔离；
- **回滚不是重新创建。** 回滚要求原沙箱的身份和 API 连接继续可用，同时让文件、内存和设备回到同一个历史点。

SDK 文档把这三种语义直接暴露出来：快照可以独立于源沙箱存活，clone 可以从运行状态派生多个副本，rollback 原地恢复并继续执行。[快照、回滚与克隆接口](https://github.com/TencentCloud/CubeSandbox/blob/v0.7.2/docs/zh/guide/snapshot-rollback-clone.md)

## 二、磁盘快照：XFS reflink 为什么能“接近零拷贝”

### 2.1 普通复制为什么不适合 Agent

假设模板 rootfs 有 20GiB，评测平台要派生 1,000 个环境。逐个复制会产生两种压力：第一，20TiB 的写入量会让存储和网络成为瓶颈；第二，复制时间与镜像大小绑定，沙箱创建无法做到细粒度供给。

CubeCoW 在支持 reflink 的 XFS 上使用 `FICLONE`。它创建一个新的文件映射，让新文件与源文件暂时共享底层数据块；源或目标发生写入时，文件系统再把被修改的块分裂成独立副本。创建动作主要更新 extent 和引用计数元数据，因此在稳定 workload 下接近 O(1) 的元数据操作，而不是 O(文件大小) 的全量拷贝。

“接近 O(1)”有两个限定：FICLONE 仍受文件系统、extent 数量、空间压力和同步策略影响；它降低的是初始复制量，不代表后续写入没有成本，也不代表快照永远零磁盘占用。

### 2.2 CubeCoW 在 reflink 之上做的管理

裸 `FICLONE` 只提供系统调用，平台还需要回答“卷叫什么、谁拥有、崩溃后怎么恢复、删除哪个快照会不会伤到其他快照”。CubeCoW 的设计文档和源码体现了几项工程选择：

1. **卷和快照有明确命名空间。** 新建卷、快照和克隆都需要在并发下抢占唯一名称，不能靠“先查再写”的非原子流程；
2. **文件系统是重要的事实来源。** 启动或恢复时可以扫描卷目录和快照文件，重建内存索引；崩溃残留和零字节文件要有处理策略；
3. **快照链尽量扁平。** 派生快照不应让每次读写都递归追踪长链，否则删除、恢复和容量估算都会越来越复杂；
4. **删除是引用计数变化。** 删除一个快照的主要动作是去掉文件名和减少共享 extent 的引用，其他快照继续指向自己的映射；
5. **目录、元数据和数据块有一致性顺序。** 先抢名、再执行 clone、最后落盘目录状态，崩溃恢复才能判断某个对象是否完成。

这些选择让 CubeCoW 关注“存储对象的生命周期”，而不是把 XFS 当作一个不可见的黑盒。详细的 reflink 路径可见项目的快照深潜文档。[CubeCoW 快照原理](https://github.com/TencentCloud/CubeSandbox/blob/v0.7.2/docs/zh/blog/posts/2026-06-25-cubesandbox-snapshot-clone-rollback-deep-dive.md)

## 三、内存快照：三种 SnapshotType 对应三种账本

### 3.1 Full：完整状态的基线

Full 快照保存完整 guest 内存和设备状态。它的优点是语义简单、恢复路径清晰，适合作为第一份基线、跨版本迁移的保守选项或需要独立归档的状态。代价是写入量与 guest RAM 相关，几十 GiB 的 VM 不能频繁采用这种模式。

### 3.2 Incremental：把匿名页作为变化线索

CubeSandbox 的恢复路径经常通过文件映射建立 guest RAM。对一个从内存镜像恢复的 VM 来说，只读访问的页仍可由文件页和共享 page cache 提供；第一次写入时，内核触发 CoW，页面变成该 VMM 进程的匿名页。于是可以用 `pagemap` 中的匿名页信息近似判断“这个 VM 启动后真正写过哪些页”。

Incremental 模式的关键不是“只保存某些页面，然后把其他页面丢掉”，而是：

1. 先以父快照或已有内存文件作为完整基线；
2. 识别本轮需要写入的匿名页；
3. 在 CoW 文件上只覆盖这些范围；
4. 恢复时把新文件与父级共享状态组合起来。

这个方法适合从模板启动后只修改少量工作集的 Agent，但它依赖恢复映射、父级快照和写入范围之间的严格配合。匿名页判断是实现细节，不应被写成跨平台的通用“内存变化 API”。

### 3.3 SoftDirty：真正按写入位追踪的增量

Soft-dirty 是 Linux 提供的页级写入追踪机制。系统在一次快照完成后清理 soft-dirty 标记，下一轮通过 `/proc/<pid>/pagemap` 的 bit 55 找到自上次清理以来被写过的页，再与匿名页条件结合，得到更接近“本轮真变化”的集合。

源码中的 `SnapshotType` 枚举包含 `Full`、`Incremental` 和 `SoftDirty`。SoftDirty 需要内核配置支持；如果当前环境不具备对应能力，代码路径可能回退到匿名页增量方式。这个回退很重要：接口接受了 `soft-dirty`，不等于每台节点都真的按 bit 55 工作。[SnapshotType 枚举](https://github.com/TencentCloud/CubeSandbox/blob/v0.7.2/hypervisor/vm-migration/src/lib.rs)

三种模式可以画成一张“证据账本”：

| 模式 | 变化判断 | 写入成本 | 语义风险 |
|---|---|---|---|
| Full | 不判断，保存全部 | 高 | 最简单，容量与时间重 |
| Incremental | 依赖匿名页与 CoW 基线 | 中 | 父级基线、映射语义必须一致 |
| SoftDirty | 匿名页 ∩ soft-dirty 页 | 低到中 | 依赖内核能力、清理时序和并发正确性 |

不要把“只写少量页”理解成“快照只包含少量内存”。快照的逻辑状态仍然必须完整，少写依赖的是父级数据、共享文件和恢复协议。

## 四、Clone：把一个状态变成一群可独立工作的状态

### 4.1 克隆的三个阶段

一个可靠的 `clone(n=N)` 可以抽象为：

```text
冻结或捕获源状态
    ↓
生成临时或持久快照
    ↓
对 rootfs、内存和设备状态做 N 次派生
    ↓
为每个副本建立新的 sandbox_id、网络和策略
    ↓
全部成功则返回；中途失败则清理已完成副本
```

SDK 文档明确把 clone 描述为从运行中的沙箱继承当前文件和内存状态，之后各副本写入互不影响；批量 clone 可以设置并发度，部分失败时清理已经创建的副本。这种“要么得到 N 个，要么报错并清理”的接口语义，对批量评测比“尽力创建，调用者自己找孤儿”更可操作。

### 4.2 CoW 共享的边界

克隆初始共享的是底层数据块、内存镜像或文件页，不是共享一个可变工作区。以下几类状态必须分别处理：

- guest 文件系统写入由文件系统 CoW 隔离；
- guest 内存写入由 MAP_PRIVATE/内存快照语义隔离；
- 网络连接和 NAT 会话不能从源沙箱原样共享，副本需要新 TAP、IP、策略和会话；
- 凭据策略要按副本重新绑定租户和任务，不能把源沙箱的临时授权复制给所有分支；
- 审计事件必须使用新的 sandbox_id，同时保留父快照或源任务关联。

这也是“克隆一个 VM”与“复制一个目录”的差别：状态包括进程、设备、网络和权限，而不只是文件。

### 4.3 并行评测的供给曲线

批量评测通常是先创建大量副本，再让模型独立运行，最后集中销毁。它的压力不是一个固定的“并发数”，而是三个阶段：

1. 创建洪峰：模板克隆、内存恢复、TAP 注册和策略写入集中发生；
2. 稳态运行：每个副本有不同的 CPU、IO、网络和运行时长；
3. 销毁长尾：快照、卷、网络 map、日志和 artifact 的清理时间不一致。

如果只用平均创建时间乘以副本数，无法解释排队和长尾。评测平台要记录每个副本的出生状态、模板版本、模型版本、退出原因和清理结果，才能区分“模型错”“环境错”“供给失败”和“判定器错”。

## 五、Rollback：为什么“原地恢复”比重建复杂

### 5.1 身份不变，状态改变

回滚最有价值的地方是保留 sandbox_id。Agent 可以在同一个会话中完成：

```text
checkpoint A
  → 执行步骤 B
  → 发现结果错误
  → rollback(A)
  → 调整策略
  → 继续执行步骤 C
```

如果回滚被实现成“销毁旧沙箱，再创建一个新沙箱”，文件状态可能相同，但连接、任务标识、审计链、外部路由和用户看到的环境都发生了变化。原地回滚需要暂停或停止当前 VM，替换 rootfs 与内存快照，恢复设备状态，重新建立网络和 guest agent，然后让同一个对象回到可执行状态。

### 5.2 一致性不是单个文件的问题

假设在创建快照时，guest 正在写文件、内存里的索引也正在更新。如果只保存文件系统，恢复后可能得到“索引指向不存在的文件”；如果只保存内存，文件系统又可能已经前进。快照点需要定义一个一致性边界：

- 暂停 guest vCPU 和必要设备；
- 刷新或记录 rootfs/卷的 CoW 状态；
- 保存 VMM 设备和内存状态；
- 记录模板、内核、镜像、agent、CPU、内存和磁盘规格；
- 以同一个快照 ID 发布状态。

现实系统还要处理外部世界：TCP 连接、外部数据库事务、对象存储上传和队列消息不会因为 VM 回滚自动回滚。**沙箱回滚保证的是沙箱内部状态，不是外部副作用的时间旅行。**

### 5.3 版本匹配是恢复的前置条件

源码中的快照元数据会记录 VMM 版本、内核版本、镜像版本、资源规格以及可选的 guest agent 版本，并在恢复前比较兼容性。这个检查不是形式主义：设备状态布局、内存区域、内核命令行和 agent 协议一旦变化，恢复一个旧状态可能得到一个“启动了但行为不对”的沙箱。

因此模板升级要有明确策略：

- 旧快照只由兼容的 VMM 和 guest agent 恢复；
- 新模板不能默认覆盖旧模板的 ID；
- 恢复失败要有可读的版本不匹配错误；
- 评测结果必须记录模板和 VMM 版本，否则以后无法复现。

## 六、跨节点快照：把状态搬走，也把成本搬走

本地快照的速度来自节点本地文件、page cache 和 CoW。跨节点恢复则需要把 rootfs、内存文件和元数据放到共享对象存储或其他可达后端，再由目标节点下载或按需读取。CubeSandbox v0.7 文档和更新日志已经把 S3 跨节点暂停/恢复列为能力方向，但“能跨节点恢复”不等于“没有迁移成本”。

跨节点流程至少包含：

1. 源节点暂停并生成可恢复的快照；
2. 上传 rootfs/内存卷和元数据；
3. 目标节点确认内核、VMM、CPU、磁盘和 agent 能力匹配；
4. 目标节点建立本地映射、TAP 和策略；
5. 恢复 guest，做健康检查并更新控制面路由；
6. 源节点按保留策略清理或保留旧状态。

迁移期间要处理两种失败：上传部分完成、目标节点恢复部分完成。对象存储的临时对象、目标端半成品卷和旧路由都需要幂等清理。企业如果把跨节点快照当成“免费高可用”，最终会在网络、存储和恢复长尾上付账。

## 七、横向参照

| 方案 | 状态能力 | 优势 | 适用边界 |
|---|---|---|---|
| Docker overlayfs | 文件层 CoW，进程状态通常重建 | 简单、生态成熟 | 不提供独立内核和完整 VM 状态 |
| CRIU | 进程/容器检查点 | 对特定进程树可细粒度恢复 | 内核、设备、网络和外部连接兼容性复杂 |
| Firecracker snapshot | VM 内存、设备和磁盘快照 | Serverless 友好、路径清晰 | 由调用方负责更上层模板、策略和生命周期 |
| E2B | 平台化模板、快照、pause/resume 与 SDK | Agent 使用门槛低 | 具体状态和运营边界受平台形态影响 |
| CubeCoW + CubeHypervisor | rootfs CoW + VM 内存/设备快照 + Agent 生命周期 | 克隆、回滚、暂停和评测语义统一 | 需要维护本地存储、版本和恢复兼容性 |

CubeSandbox 的差异不是“有一个 FICLONE 调用”，而是把磁盘、内存、VMM 和 Agent API 组合成了一个对上层有意义的状态模型。

## 八、企业视角：快照既是性能机制，也是治理机制

**对评测团队**，快照是实验控制变量。模板 ID、依赖锁文件、内核、agent 和快照祖先共同定义“模型看到的世界”。没有这些元数据，分数无法复核。

**对平台团队**，快照是供给机制。预热模板可以把启动从冷 boot 变成 restore，clone 可以让批量任务共享初始数据，但本地模板副本、磁盘水位和 page cache 也会成为新的容量约束。

**对安全团队**，快照是潜在的凭据放大器。运行中不应进入 guest 的密钥如果错误地进入了内存或文件，快照、克隆和跨节点复制会把它复制到更多位置。凭据注入要与快照策略协同：代理侧密钥不进入 guest，快照侧才不会保存它。

**对合规团队**，回滚会改变“当前状态”，但不应删除审计事实。日志必须保留 task、snapshot、rollback 和分支关系，让审计者知道某个结果是在什么状态上产生的。

## 九、成本账：快照省下什么，又新增什么

快照的收益可以分成三项：

```text
收益 ≈ 省掉的冷启动时间 + 省掉的重复镜像拷贝 + 提高的环境复现率
```

成本也有三项：

```text
成本 ≈ 本地/对象存储占用 + 快照扫描与写入 IO + 元数据与清理运维
```

如果每个快照的逻辑大小是 20GiB，但本轮只写了 300MiB，CoW 的物理增量可能接近 300MiB 加元数据，而不是再写 20GiB。这个“可能”取决于工作集写入、extent 分裂、父级快照、文件系统空间和内存变化，不能把逻辑大小直接当成物理成本。

平台要设置快照 TTL、祖先保留、最大分支数、单租户存储配额和清理重试。`with` 语句结束不代表快照自动删除；快照生命周期必须有独立的回收任务和告警。

## 本章小结

| 关键认知 | 一句话 |
|---|---|
| 两种状态 | VM 状态 = 磁盘 CoW + 内存/设备快照，缺一边都不能完整恢复 |
| FICLONE | 主要共享 extent 元数据，接近零拷贝创建，但后续写入和空间成本仍存在 |
| 三种 SnapshotType | Full 保守完整，Incremental 依赖匿名页与基线，SoftDirty 依赖写入位与内核支持 |
| Clone | 从同一状态派生多个新身份，文件、内存、网络、凭据和审计都要重新隔离 |
| Rollback | 保持 sandbox_id 原地恢复，内部状态可回退，外部副作用不会自动回滚 |
| 版本与清理 | 快照要记录兼容元数据，跨节点和 TTL 清理要有幂等与审计 |

## 思考题

1. 一个 20GiB rootfs 的沙箱执行了 300MiB 写入后创建快照。哪些数据仍可由父快照共享？哪些操作会触发新的物理块？如果同时创建 50 个 clone，存储成本的上界和下界分别由什么决定？
2. 对同一 VM，Full、Incremental 和 SoftDirty 三种模式分别适合什么场景？如果 SoftDirty 在某台节点不可用，平台应拒绝请求、回退还是标记快照能力降级？请说明复现性和安全代价。
3. Agent 在快照后向外部数据库提交了一笔事务，随后 rollback。沙箱内部和数据库外部各处于什么状态？你会如何用幂等键、事务日志或补偿操作处理这个时间差？
4. 评测平台要从一个模板派生 1,000 个副本。请把创建洪峰、运行长尾、销毁长尾分别列出瓶颈，并给每个阶段配置一个可观测指标。
