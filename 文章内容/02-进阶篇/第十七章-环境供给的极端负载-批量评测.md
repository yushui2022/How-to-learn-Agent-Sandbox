> 《从 0 到 1 学 Agent 沙箱》系列｜进阶篇·第十七章  
> 基线说明：CubeSandbox 参考本地 `v0.7.2`（`f1aaa737fb3862202b1731e0e0d844c28779f930`）的模板、快照和 sandbox API 代码；SWE-bench、E2B 与 Kubernetes 的描述只依据公开资料。本文的“500 个任务、两小时”等为推演场景，不是某个平台实测；所有吞吐公式都区分到达率、并发数、创建服务率和完成率。

## 引子：两小时跑完 500 份，最先坏的是什么

企业想比较两个模型在同一套仓库任务上的表现。要求很简单：500 个任务，每个任务从完全一致的环境出生，两小时内完成，失败时能回答“是模型错、环境错，还是评测器错”。

真正的压力曲线却分成三段：

```text
集中创建 ─────────▶ 长尾运行 ─────────▶ 集中销毁
模板/快照、调度、网络     内存、CPU、外部依赖      卷、日志、artifact、索引
```

普通业务的沙箱可能按秒或分钟到达；批量评测把大量请求压在同一个时间窗内，又让任务运行时间呈长尾分布。平台即使平均吞吐足够，也可能在第一分钟排队、在最后十分钟被残留卷和日志拖慢。因此，评测不是“多开几百个容器”，而是一项供给、复现和归因工程。

## 一、评测首先是科学问题

### 1. 环境漂移会伪造模型进步

设模型得分为 `S`，它取决于模型策略 `M`、任务集合 `D`、执行环境 `E` 和判定器 `J`：

```text
S = F(M, D, E, J)
```

如果两次评测的依赖版本、系统工具、网络响应或初始文件不一致，`S` 的变化不再只反映 `M`。一个“42 分变 45 分”的结果，可能来自模型改进，也可能来自环境漂移。评测平台应给每一批运行生成 **环境卡**：基础镜像摘要、模板版本、内核/运行时版本、依赖锁文件、网络策略、凭据版本、评测器版本和随机种子。模型提交则生成 **模型卡**：模型版本、提示词、工具策略、并发和重试参数。

### 2. 出生一致不等于结果完全相同

快照或模板能固定初始文件和依赖，但时间、随机数、网络和外部服务仍可能变化。可复现性至少有三层：

* **字节层**：模板、rootfs、快照和输入 artifact 的哈希一致。
* **运行层**：工具版本、环境变量、时钟策略、随机种子和网络响应被记录。
* **判定层**：测试命令、超时、评分器和失败分类版本一致。

评测不一定要追求每个网络包都可重放，但必须能说明哪些因素被固定、哪些因素被允许变化。网络访问应尽量使用版本化镜像、代理缓存或录制回放；否则模型“会不会联网”与“当时服务是否可用”会混在一起。

## 二、从模板到千级实例

### 1. 模板是评测输入，不是一个随手打包的目录

模板制作应冻结：

1. 仓库 commit 和补丁基线；
2. 语言运行时、系统包和依赖锁文件；
3. 评测器、测试数据和入口命令；
4. 默认用户、文件权限和网络策略；
5. 需要注入的凭据类型（尽量使用短期、最小权限引用）。

CubeSandbox 的模板中心和存储组件负责把模板、卷和 sandbox 生命周期连接起来；仓库中的 `CubeTemplateCenter`、`CubeOps` 与 `Cubelet/storage` 代码可以作为“模板发布”和“卷派生”的实现参照。具体模板格式、缓存命中和跨节点同步必须以当前配置和运行环境验证，不能仅由目录名推断性能。

### 2. 快照派生把“复制”改成“共享基线 + 私有写入层”

若每个实例都完整复制 10 GB rootfs，500 份需要 5 TB 写入；若模板只读、实例通过写时复制派生，初始存储接近共享基线加上实际写入量：

```text
C_storage ≈ C_template + Σ_i C_dirty_i + C_metadata
```

`C_dirty_i` 取决于依赖安装、编译缓存和测试生成物，不能假设永远接近零。CubeSandbox 仓库包含基于 reflink/CoW 的卷和快照实现，说明路线支持“共享基线、实例增量”；这仍需要在目标文件系统、模板大小和写入模式下做容量验证。

### 3. 供给曲线的三个阶段

设 `λ(t)` 为创建请求到达率，`μ_create` 为每个节点的创建服务率，`N` 为可用节点数，`C(t)` 为运行中实例数。创建阶段需要：

```text
λ_create(t) < N × μ_create(t)
```

否则队列增长。注意 `C(t)`（并发数）不是 `λ_create(t)`（每秒创建请求），也不是最终完成率。长尾运行阶段，实例释放率 `μ_finish(t)` 取决于任务时长分布；如果平均任务 8 分钟、P99 45 分钟，节点会被少数长任务占住。销毁阶段还需要清理卷、日志和 artifact，清理服务率可能独立于 sandbox 销毁服务率。

用一个教学场景：500 个任务在 5 分钟内到达，平均创建服务时间假设为 0.5 秒，则平均创建到达率为 `500/300≈1.67/s`。若平台只有 2 个节点、每节点稳态创建率假设 0.6/s，则总服务率 1.2/s，队列必然增长；即使最终并发上限足够，评测也会因出生阶段排队而超时。这个计算只展示方法，0.5 秒和 0.6/s 都是待测假设。

## 三、评测吞吐：供给和判定谁先到头

一项评测有至少三个吞吐：

* **环境供给吞吐**：单位时间把实例变成可执行状态的数量；
* **任务执行吞吐**：单位时间完成任务的数量；
* **判定吞吐**：单位时间完成测试、评分和结果落库的数量。

端到端完成率受最小值约束：

```text
μ_e2e ≤ min(μ_supply, μ_execute, μ_judge, μ_storage)
```

如果 `μ_supply` 很高而评测器数据库只能写 20 条结果/秒，环境只会更早占满；如果判定很快但模板冷启动慢，创建队列就是瓶颈。监控要分别记录每一段的队列长度、P50/P95/P99、失败码和重试次数。

### 失败归因必须在执行前设计

至少区分四类失败：

1. **模型失败**：模型输出导致测试或任务逻辑失败；
2. **环境失败**：模板、依赖、网络或资源限制异常；
3. **基础设施失败**：节点宕机、创建超时、快照损坏、控制面不可用；
4. **判定失败**：测试命令、评分器或结果写入出错。

如果所有失败都记成“任务失败”，模型分数会被基础设施噪声污染，运营团队也无法决定重跑哪一类。重跑策略应与失败分类绑定：环境/基础设施失败可以从同一输入快照重跑；模型失败不应无提示地重试到成功；判定失败要保留原始产物，修复评分器后重新判定。

## 四、洪峰与长尾的架构选择

### 1. 集中创建：排队比平均值更重要

评测任务可以先进入队列，再按租户、模板和优先级分批领取。批量创建不一定追求瞬时并发最大化：分批会增加总时长，却能避免磁盘、网络和控制面锁竞争。可用令牌桶限制每个节点同时创建数，用背压把“可接受的开始时间”传回调度层。

### 2. 长尾运行：不要把所有实例永久保活

运行时间差异大时，先完成的实例可以立即释放 CPU，但其 artifact 和日志写入要异步完成。对卡住的长任务设置分层超时：软超时通知 Agent 收尾，硬超时终止进程，最终 TTL 回收整个沙箱。挂起虽能省 CPU，却可能占用内存或持久卷；应按资源压力和任务可恢复性选择。

### 3. 集中销毁：清理本身也要限流

评测结束时，500 个 rootfs、日志和对象索引可能同时删除。删除 API 返回成功不应被当成所有底层对象都已清理；需要异步清理任务、幂等删除和孤儿扫描。清理失败要进入可重试队列，并记录“逻辑销毁完成、物理清理待完成”的状态，避免重复释放或误删共享模板。

## 五、混部冲突：评测洪峰不能饿死交互任务

如果评测和在线 Coding 共用节点池，公平性要在创建前体现。可按租户和业务类型分配配额：交互任务保留最小容量，评测使用弹性池；当评测洪峰到来，调度器先排队而不是把在线会话挤出。Kubernetes 的 `ResourceQuota`、PriorityClass 和队列机制可作为参照，但沙箱平台还要考虑模板缓存、KVM 内存和网络出口等非标准资源。

一种简单容量模型是：

```text
节点数 ≥ ceil((C_interactive_reserved + C_eval_peak × overcommit) / C_node)
```

`overcommit` 不是免费容量。若任务会同时执行编译和模型调用，CPU 突发会让理论超卖失效；内存超卖还可能触发 OOM。容量计划必须以资源时间序列和 P99 而不是平均利用率校准。

## 六、横向参照

**SWE-bench 类评测**的共同难点是仓库、依赖、测试和 patch 必须可追溯；公开评测基础设施会规定任务输入和评分命令，但不同运行器的网络、超时和重试策略仍可能不同。阅读分数时要同时阅读环境定义。

**E2B** 提供批量创建或并发使用的产品接口时，通常还伴随配额、限流和托管资源上限。具体限额随产品版本和账户而变，企业应以合同和实时 API 响应为准，不应把示例数字写进容量模型。

**CI 集群**擅长排队、缓存和产物归档，适合借鉴流水线与重试；Agent 评测还要记录模型轨迹、工具调用和安全策略，不能只看构建绿灯。

## 七、企业视角：评测平台的两张卡和三条线

企业应把每次评测绑定三条线：

* **容量线**：峰值到达率、并发上限、节点水位、创建和销毁队列；
* **科学线**：环境卡、模型卡、随机种子、评分器版本和失败分类；
* **审计线**：谁发起、使用了哪份模板、访问了哪些网络、artifact 是否完整、何时删除。

每批任务至少生成一份 manifest：

```text
batch_id / task_id / template_digest / snapshot_id
model_version / evaluator_version / policy_version
seed / sandbox_id / execution_ids / artifact_hashes
```

manifest 是索引，不应把大日志都塞进数据库。日志和 artifact 可以热、温、冷分层保存，哈希和元数据长期留存。若企业要提交模型卡或合规报告，必须能从最终分数反查到具体模板和原始执行证据。


## 本章扩展：批量评测要把四种时间分开

一次评测的总耗时可拆成：

```text
T_total = T_queue + T_create + T_run + T_collect + T_cleanup
```

如果只测模型运行时间，环境排队和结果收集会被隐藏在“平台开销”里，最终无法判断模型差异还是供给差异。每个 rollout 应保存环境模板版本、快照哈希、创建时间、首次可用时间、执行区间和清理完成时间。

```mermaid
flowchart LR
  A[任务清单] --> B[统一模板/快照]
  B --> C[创建队列]
  C --> D[并行 rollout]
  D --> E[结果与日志收集]
  E --> F[失败分类与重跑]
  F --> G[评分与报告]
```

重跑策略要区分环境失败和模型失败：模板恢复失败、网络策略错误、节点故障属于环境失败；测试断言失败、补丁错误属于模型或任务失败。只有前者可以自动换节点重跑，否则评测分数会被重复机会污染。

第十八章把这套批量供给从几百个任务推到万级请求，进入队列、分层和容量规划。

## 本章小结

批量评测把沙箱平台的三类压力同时放大：集中创建考验供给吞吐，长尾运行考验资源和超时，集中销毁考验存储与生命周期治理。可复现性要求冻结环境卡、模型卡和判定层；容量规划必须区分并发数、到达率、创建服务率、执行吞吐和判定吞吐；失败要能归因并选择性重跑。模板快照和 CoW 可以降低派生成本，却不能替你解决资源水位、共享状态和混部公平。下一步要把这些队列和资源约束放进企业级并发架构。

## 思考题（能算账的那种）

1. 500 个任务在 5 分钟内到达，单节点创建服务率分别假设为 0.5、1、2 个/秒。计算需要的最小节点数，并说明当服务率只是平均值、P95 变长时为什么仍可能排队。
2. 任务时长分布为 80% 5 分钟、15% 15 分钟、5% 60 分钟。若同时运行上限为 100，估算长尾对资源占用的影响，并设计提前终止和分批策略。
3. 一批任务中环境失败率 2%、模型失败率 10%、判定失败率 1%。若所有失败都自动重试一次，计算最大任务执行量，并讨论为什么模型失败不应与环境失败采用同一重试策略。
