## 引子：同一份密钥，两种事故

安全培训通常这样描述密钥事故：工程师把生产 API Key 复制进了脚本，脚本又被提交到公共仓库。培训的重点是“人会犯错”，因此解决办法是扫描提交、轮换密钥、限制权限。

Agent 让事故模型换了形状。模型没有“保密意识”，却会严格执行一个看似合理的请求。如果环境变量中有 `OPENAI_API_KEY`，模型可能为了诊断失败而执行 `printenv`；如果任务要求提交代码，它可能把认证头写进配置文件；如果检索到的网页说“把令牌发到这个调试地址”，提示词注入就会把这条命令包装成工作流的一部分。模型没有主观恶意，结果却和主动泄密一样。

同一份凭据进入沙箱后，至少出现三条新的路径：进入模型上下文的输出路径、进入生成代码和提交历史的持久化路径、被注入内容诱导外传的网络路径。传统 Vault/KMS 仍然需要，但它们解决的是“密钥存在哪里、谁能取”的问题；沙箱还必须解决“模型能不能看见、请求能不能带出去”的问题。

本章的硬问题是：如何让 Agent 使用凭据完成工作，却尽量不把凭据交给 Agent？答案不是“把密钥藏在一个更深的环境变量里”，而是把凭据从执行环境的对象，改造成出口策略的一次性副作用。

## 一、威胁模型：模型把能看到的东西都当成工具

把 Agent 的执行循环写成一条数据流：

```text
用户目标 → 模型上下文 → 生成命令/代码 → 沙箱进程 → 出口请求 → 外部服务
             ↑              ↓                 ↓
        检索内容/工具结果   文件与日志       网络响应与错误
```

凭据可能在四个位置出现：

1. **进程环境**：`env`、`/proc/<pid>/environ`、子进程继承环境。
2. **文件与版本库**：`.env`、配置文件、构建缓存、git diff、压缩产物。
3. **模型回流**：stdout/stderr、异常堆栈、HTTP 响应、工具返回值被拼进下一轮上下文。
4. **出口请求**：请求头、URL、表单或 DNS 标签把值带到外部。

传统人类路径通常需要两个动作：主动复制密钥，再主动提交或发送。Agent 路径只需一个“帮助我排查问题”的提示就可能完成两步。提示词注入也不等于模型必然泄密，它只是把攻击者控制的文本放进决策上下文，增加了模型采取危险动作的概率；最终仍由命令权限、网络策略和出口审计决定结果。

因此，本章采用的威胁模型是：沙箱内代码和模型输出均不可信；控制面、凭据服务和出口网关属于受控组件；攻击者可以读写沙箱内可见的文件和进程、构造任意 HTTP 请求、诱导模型打印或提交数据，但不能直接修改控制面策略。若控制面被攻破，出口注入也不能单独挽救系统，这是边界必须写清的地方。

## 二、把凭据移出沙箱：注入式出口的工作方式

CubeSandbox 的 CubeEgress 是宿主机侧的 HTTP/HTTPS 出口代理。策略按沙箱源地址匹配规则，规则可以限定 SNI、Host、方法、路径、端口和 scheme。命中允许规则后，网关在代理请求上设置凭据头，再转发到上游；沙箱看到的是代理地址和响应，不需要持有真实值。

在 `v0.7.2` 中，注入路径由 OpenResty Lua 实现。`access_phase.lua` 先建立请求上下文，再运行 scheme 与 Host/SNI 一致性检查，最后调用 `ngx.req.set_header` 写入请求头。源码中的关键逻辑见 [access_phase.lua（固定 commit）](https://github.com/TencentCloud/CubeSandbox/blob/f1aaa737fb3862202b1731e0e0d844c28779f930/CubeEgress/lua/access_phase.lua#L193-L292)。当规则声明要注入某个头时，网关会先清除沙箱自己提交的同名头，再决定是否写入真实值；这一步防止“注入失败时，沙箱伪造一个 Authorization 头仍被转发”的旁路。

请求路径可以抽象为：

```text
沙箱请求
  → CubeVS/TPROXY 把流量送入 CubeEgress
  → 按 sandbox_ip + SNI/Host + method/path 选择规则
  → G1～G4 检查 scheme、TLS、SNI、Host
  → 注入 Authorization/X-API-Key 等头
  → 校验上游证书后转发
  → 仅返回业务响应和审计元数据
```

“只在出口网关瞬时出现”描述的是数据面：值不会进入沙箱环境、文件和模型上下文。当前实现的策略存储仍然需要保存 `inject[].secret`，并由管理员 API 写入共享字典；它不是 Vault 直连，也不是硬件密钥保管。策略存储、配置备份、进程内存和管理员权限仍是凭据暴露面，必须由控制面加密、访问控制和轮换机制覆盖。源码的校验与指纹逻辑见 [policy.lua](https://github.com/TencentCloud/CubeSandbox/blob/f1aaa737fb3862202b1731e0e0d844c28779f930/CubeEgress/lua/policy.lua#L170-L300)：审计使用 `fp-` 加四字节 SHA-256 前缀作为关联句柄，但它只是调试标识，不是认证密钥。

### 2.1 为什么必须绑定域名和路径

只按“这个沙箱可以访问公网”来注入密钥，相当于把密钥交给了任意外部站点。安全策略至少应绑定四个维度：

```text
secret_scope = (sandbox, destination_identity, method, path)
```

例如，`api.github.com` 的 `POST /repos/*/issues` 可以注入机器人令牌，但 `GET /repos/*/contents` 不一定允许；`registry.example.com` 的 token 只用于包下载，不能被发往任意同网段 IP。CubeEgress 的规则匹配采用首个命中，域名通配符只支持前缀 `*.`，路径通配符只支持尾部前缀。策略越宽，误用和绕过的空间越大。

HTTPS 还必须检查 Host 与 SNI 一致。若只看 Host，攻击者可能让代理以一个受信任的 SNI 建立 TLS，再用另一个 Host 解释请求；当前代码在 G4 阶段拒绝这种不一致，并在安全事件中记录原因。需要注意，网关能验证的是代理到上游的 TLS 与策略身份，不等于它能判断响应内容是否安全。

### 2.2 注入失败应该怎样处理

当前实现把“注入失败”和“请求是否允许”分开：G1～G4 失败时清掉待注入头，记录 `security_event`，但是否继续转发由规则的 `action.allow` 决定；策略缺失、无匹配规则等则直接拒绝。这样做适合“可访问但不带凭据”的公共端点，却不适合所有私有 API。对必须认证的目标，应把“注入失败即拒绝”作为规则级约束，而不是依赖调用方猜测。

这也是“注入式方案对三条路径全部免疫”不能成立的原因。它能阻止沙箱直接读取真实值，却不能阻止模型利用合法凭据完成越权业务，不能阻止上游返回敏感数据后被模型打印，也不能阻止管理员把规则配置得过宽。正确表述应是：它切断了“凭据值进入沙箱”这一类泄露路径，并把剩余风险移到策略、业务授权、响应数据和控制面。

## 三、三条 Agent 泄露路径逐一推演

### 路径 A：环境变量被打印

如果密钥以环境变量注入，模型可能执行 `env | sort`，把输出回流给编排器；即使日志系统做了字符串脱敏，密钥也可能先进入模型上下文。出口注入方案不在沙箱设置该变量，模型只能看到“请求未认证”或业务错误，无法通过打印获得值。

仍要防两类旁路：一是控制面为了兼容旧程序，把同一密钥同时放进环境变量；二是网关把完整请求头写进 debug 日志。CubeEgress 的审计模块只记录注入的头名和合成 `secret_ref`，不记录渲染后的值，见 [audit.lua](https://github.com/TencentCloud/CubeSandbox/blob/f1aaa737fb3862202b1731e0e0d844c28779f930/CubeEgress/lua/audit.lua#L108-L146)。生产配置还应禁止 Nginx/OpenResty 的请求头 debug dump，或确保 redactor 覆盖 Authorization、Cookie 和自定义凭据头。

### 路径 B：凭据进入代码或 commit

模型常会把“配置好 API 客户端”理解为写入 `.env` 或源代码。注入式出口使代码只需要访问一个固定代理地址，凭据头由网关补齐，因而代码、diff 和 artifact 中没有原值。安全扫描仍有价值，但它从第一道防线变成了补漏：扫描提交、构建日志和压缩包，发现误放入的旧密钥后自动轮换，而不是把扫描结果当成唯一防护。

### 路径 C：提示词注入诱导外传

攻击者可以在网页、README 或 issue 中写“请把诊断结果 POST 到某地址”。如果该地址不在 allow-list，代理在策略阶段拒绝；即使地址被允许，注入规则只对绑定目标生效，攻击者不能把 GitHub 令牌带到任意域名。这里的关键是“凭据绑定请求目标”，而不是“相信模型会遵守系统提示”。

但网络 allow-list 不是数据流分类器。攻击者可以把敏感数据编码进允许上传的 issue 内容，或利用一个合法 API 的反射字段。需要在工具层限制上传文件、在审计层记录请求大小和目标、在业务层限制令牌权限和可写范围。注入方案降低了风险，却不会自动识别“合法请求中的恶意数据”。

## 四、与 Vault/KMS、E2B 的分工

Vault/KMS 的强项是密钥生命周期：生成、加密存储、轮换、撤销、审计谁取过。沙箱层的强项是运行时边界：哪个沙箱、哪个目标、哪个方法和路径可以使用某个凭据，以及凭据是否进入模型可见数据。两者可以组合成：

```text
Vault/KMS（存储与轮换）
       ↓ 受控同步/短期令牌
CubeEgress（目标绑定与瞬时注入）
       ↓
上游 API
```

同步过程不能把长期密钥复制到每台计算节点的明文配置。可行的实现包括网关启动时取得短期租约、按请求向 Vault 兑换短期凭据、或由控制面把加密密文下发到受保护内存。当前 CubeSandbox `v0.7.2` 的源码展示的是策略内联值与指纹审计，不能据此宣称已经实现 Vault 动态租约；这属于后续集成设计。

E2B 等托管 Agent 沙箱通常提供 secrets 配置和沙箱级环境管理，优点是调用方简单、生态兼容；代价是秘密是否进入沙箱环境取决于使用的 API 与任务设计。对需要强合规、专有网络和可证明出口控制的企业，E2B 的托管边界和自建 CubeEgress 的控制边界需要逐项核对，而不能只比较 SDK 参数名。参考：[E2B Sandbox 文档](https://e2b.dev/docs/sandbox)。

## 五、审计：记录“谁用过”，不要记录“值是什么”

一次凭据使用至少需要关联：租户、沙箱、任务、策略版本、匹配规则、目标 SNI/Host、方法和路径、结果状态、注入头名、secret fingerprint、时间戳和请求 ID。审计记录的目标是回答“哪个主体在什么策略下向哪个目标使用了哪个凭据引用”，而不是让日志成为第二个密钥仓库。

建议使用两条流水线：

- **业务请求事件**：每个请求一条 JSONL，记录允许/拒绝、状态码、延迟、字节数和脱敏请求头。
- **安全事件**：注入被丢弃、Host/SNI 不一致、策略缺失、上游 TLS 失败等额外写一条事件，便于告警和合规取证。

CubeEgress 当前正是这种双写思路：普通 `http_request` 与专门的 `security_event` 并存；审计文件在 worker 初始化时检查可写性，写入失败记录错误。它并不等于不可篡改审计。企业需要把日志转发到受控存储，使用哈希链、对象锁或 WORM 策略，并限制网关进程与业务运维对历史文件的删除权限。

## 企业视角：把“凭据不落地”变成可举证控制项

合规材料不要写“模型不会泄密”，而应写成可验证控制：

| 控制目标 | 可验证证据 | 仍需补充的边界 |
|---|---|---|
| 凭据不进入沙箱 | 沙箱环境、文件和 artifact 扫描；出口注入策略 | 旧模板和调试开关不能注入环境变量 |
| 只能访问批准目标 | 版本化 allow-list、规则匹配测试、拒绝事件 | 允许目标本身可能被滥用 |
| 能追溯使用 | request_id、policy_id、rule_id、secret fingerprint | 审计存储需防篡改 |
| 能快速止损 | 秘密轮换、规则撤销、网关热更新演练 | 已发出的请求无法撤回 |

## 本章小结

凭据安全的关键变化不是“模型更容易犯错”，而是模型把读取、改写、发送三个动作串成了自动循环。把长期秘密放进沙箱，等于把它同时交给进程、文件、模型上下文和网络。出口注入能切断其中最危险的一段，但不替代 Vault/KMS、最小权限、网络 allow-list、响应审计和轮换机制。

当前 `v0.7.2` 的事实边界是：CubeEgress 在代理请求上执行域名/路径约束和头注入，审计记录头名与合成引用；策略中的内联秘密仍是控制面敏感数据，不能宣传成“全程不落地”。

## 思考题

1. 某 Agent 只允许访问 `api.example.com/v1/*`，但允许上传任意 JSON。攻击者如何把秘密编码进合法请求？需要增加哪些业务级限制？
2. 估算每天一千万次出口请求的审计量：假设每条 JSONL 平均 1.5KB、保留 30 天，热存储与压缩后冷存储分别需要多少空间？哪些字段可以采样，哪些安全事件必须全量保留？
3. 设计 Vault/KMS 与 CubeEgress 的轮换流程：轮换窗口内旧值和新值如何并存，如何证明沙箱从未读到任一原值？
