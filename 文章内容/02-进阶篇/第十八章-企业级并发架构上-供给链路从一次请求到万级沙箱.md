> 《从 0 到 1 学 Agent 沙箱》系列｜进阶篇·第十八章  
> 基线说明：CubeSandbox 事实以本地仓库 `G:\Projects\agent-sandbox-series-research\CubeSandbox` 的 `v0.7.2` commit `f1aaa737fb3862202b1731e0e0d844c28779f930` 为准，重点参照 `CubeAPI`、`CubeMaster`、`Cubelet` 目录及测试。本文不从“60 ms”反推模板克隆、KVM 启动、网络配置等分段耗时；任何分段数字均明确标为假设，需在目标硬件和版本上实测。

## 引子：两万个请求同时到来

周五晚高峰，2 万个 Agent 任务几乎同时申请沙箱。每个任务都希望“马上有一个可执行环境”，但平台真正要完成的是一条供给链：接收请求、认证和限流、放入队列、选择节点、准备模板和卷、启动虚拟机、配置网络、确认健康、返回可用地址。

单机 demo 只证明链路能走通；企业平台要回答的是：哪一层先排队？哪一层有硬上限？请求超时后是否仍在后台创建？节点选择失败时如何重试？如果把所有动作塞进一个同步 HTTP 请求，控制面会被长任务拖住；如果无限重试，洪峰就会变成重试风暴。

本章把链路分为请求层、调度层和执行层。三层共享状态，但不共享故障边界：请求层负责流量和契约，调度层负责把需求映射到节点，执行层负责在节点上把模板变成可用沙箱。

## 一、先区分四个量：到达、并发、服务率、完成率

并发架构最常见的误判，是把“2 万并发”当成“每秒创建 2 万个”。四个量必须分开：

* **到达率 `λ(t)`**：单位时间进入创建队列的请求数；
* **在途并发 `L(t)`**：正在排队、创建或运行的沙箱数；
* **创建服务率 `μ_create`**：单位时间节点实际把请求变成可用沙箱的数量；
* **完成率 `μ_finish`**：单位时间任务结束并释放资源的数量。

稳定运行要求在窗口内 `λ < μ_create`；若任务运行时间长，`L` 仍可能远大于创建队列。Little 定律 `L = λ × W` 只能在稳定、定义一致的系统中使用：`L` 是系统内请求数，`W` 是从进入到离开的平均时间。不要用它把一个 60 ms 的单次样本直接乘成万级吞吐结论。

## 二、请求层：先控制洪峰，再谈低延迟

### 1. API 网关与鉴权

请求层接收模板、资源、网络、租户和幂等键。它应在进入调度前完成参数校验、身份映射和配额检查。CubeSandbox 的仓库包含 `CubeAPI` 服务和 E2B-compatible 示例；示例客户端使用 bearer token 访问 `/sandboxes`。生产网关还需要租户级权限、请求体大小限制、速率限制和审计 ID。

鉴权失败与资源不足要使用不同 reason code。否则客户端会把权限问题无限重试，或者把模板错误误判成节点短缺。API 返回的 `request_id`、`operation_id` 和 `sandbox_id` 应有清晰的生命周期：请求可能已经接受但尚未分配节点，不能因为 HTTP 连接断开就丢失状态。

### 2. 限流、排队与背压

常用的三层闸门是：

```text
租户令牌桶 → 全局创建队列 → 节点并发信号
```

令牌桶限制瞬时到达率，队列吸收短峰，节点信号防止执行层过载。队列必须有最大长度和过期策略：排队时间超过请求允许的截止时间时，应该尽早返回“容量不足/稍后重试”，而不是让请求一直占着连接。

背压要传回上游 Agent。对交互任务，可以返回重试时间和排队位置；对评测任务，可以异步提交并轮询 operation；对高风险操作，则宁可拒绝也不应在不确定状态下重复创建。重试应使用指数退避和抖动，并带幂等键。

### 3. 同步返回还是异步操作

如果创建通常在几百毫秒内完成，同步响应较易使用；但在节点扩容、模板拉取或恢复快照时，创建可能持续更久。建议把“请求被接受”和“沙箱已就绪”分成两个状态：

```text
POST /sandboxes → operation_id + 202 Accepted
GET /operations/{id} → Pending | Running | Ready | Failed
```

兼容已有 SDK 时，可以在网关内部等待一段窗口，超出窗口后返回可轮询的 operation ID。不要用客户端 HTTP 超时掩盖服务端仍在创建的事实。

## 三、调度层：从“有空位”到“合适节点”

### 1. 调度输入不是一个 CPU 数字

CubeMaster 负责接收沙箱请求并选择节点；仓库错误码中可见 `SelectNodesFailed`、`SelectNodesNoRes` 等选择失败路径。一个企业调度器至少需要以下输入：

* 可用内存、CPU、进程数和 KVM 能力；
* 模板版本和本地缓存命中情况；
* 节点健康、创建中的实例数和磁盘队列；
* 网络地址池、出口区域和租户亲和性；
* 故障域、维护状态和负载分散度。

“剩余内存最多”不一定是好节点：模板不在本地会触发拉取；网络地址池耗尽会在启动后失败；节点正在做快照也可能有高磁盘延迟。调度器应把候选过滤和打分分开，并为每个拒绝写 reason code。

### 2. 预留与确认

调度中的竞态来自多个请求同时看到同一份资源。可以先做轻量预留，再把预留令牌带到执行层：

```text
候选过滤 → 原子预留（内存/端口/模板槽位）→ 派发 → 执行层确认
```

预留必须有过期时间；执行失败或客户端取消时释放。只在调度器内扣减一个计数器，不足以防止节点本地资源变化，所以 Cubelet 仍需在创建前再次校验。

### 3. 调度延迟不是沙箱启动延迟

调度延迟包括读节点状态、选候选、写状态和发送请求。它会随节点数、租户数、锁竞争和缓存失效增长。报告 P99 时，应单独记录“排队等待”“调度决策”“执行创建”和“就绪确认”，不要把整个端到端时间平均拆成几段。尤其不能从某个 CubeSandbox 60 ms 端到端样本推断“模板克隆 10 ms、KVM 20 ms”之类的分段数字；除非有同一版本、同一硬件的 tracing，任何分段只能是待验证假设。

## 四、执行层：Cubelet 上的并发创建

### 1. 三段动作

在节点上，一个 sandbox 创建通常包含三类动作：

1. **存储准备**：从模板派生 rootfs、分配 CoW 层或恢复快照；
2. **虚拟机启动**：创建 KVM 客体、加载内核和设备模型、启动 guest；
3. **网络与就绪**：配置 TAP/虚拟网络、出口策略、vsock/sidecar 通道，等待 guest agent 或健康检查。

这三类动作可能部分并行，也可能受同一块磁盘、内核锁或地址池串行化。Cubelet 代码和配置包含 sandbox、存储与网络相关组件；具体实现路径应以 checkout 中的调用链和运行 tracing 为准。

### 2. 并发槽位和局部队列

节点不应接受无限并发创建。可为存储、KVM、网络和健康检查分别设槽位：

```text
admit_node = min(slot_storage, slot_kvm, slot_network, slot_health)
```

槽位是保护措施，不是吞吐承诺。若存储槽位很高但每次写入都会争用同一卷，实际服务率仍会下降。局部队列要支持取消、优先级和超时，并把状态返回 CubeMaster；否则控制面会认为请求仍在执行，继续派发重复任务。

### 3. 模板预热的收益与代价

预热能把模板拉取或校验从请求路径移到后台。收益取决于命中率：

```text
E[T_supply] = p_hit × T_hot + (1 - p_hit) × T_cold
```

`p_hit` 受模板版本、节点池和评测批次影响。为每个模板预热一份不等于可以无限克隆：磁盘、页缓存、内存和网络地址仍有限。预热池还要处理版本淘汰，避免旧模板继续服务新任务。

## 五、万级峰值的排队推演

设某批任务在 60 秒内到达 12,000 个，平均到达率 200/s。平台有 100 个执行节点，每节点创建服务率的**教学假设**为 3/s，则总服务率是 300/s，平均上可以消化洪峰。但若模板冷启动使服务率降到 1.5/s，总服务率只有 150/s，队列每秒增加 50 个；一分钟后仍有约 3,000 个请求等待，不含失败重试。

这不是对 CubeSandbox 或任何产品的性能结论。真实推演要把 `μ_create` 按模板、硬件、并发度和 P95 测量。服务率也不是“单次启动时间的倒数”：创建存在批处理、共享缓存、锁和尾延迟，且请求可能在网络配置或健康检查阶段失败。

过载行为可以分级：

1. **正常排队**：队列短，维持 SLO；
2. **延迟提示**：返回预计等待或异步 operation；
3. **降级**：选择备用模板、降低非关键日志或转移到弹性池；
4. **拒绝**：超过租户/全局预算，返回可重试错误；
5. **熔断**：节点或模板连续失败，暂时停止派发并进入修复。

没有拒绝边界的系统会把有限资源耗在重试和健康检查上，最终把在线会话一起拖垮。

## 六、与 K8s 调度器和 E2B 托管的参照

Kubernetes 调度器把 Pod 放入调度队列，经过过滤和打分后绑定到节点；沙箱平台可以借鉴这种分层，但 MicroVM 还要额外处理模板缓存、KVM、虚拟网络和快照。Kubernetes 的 `ResourceQuota` 和 PriorityClass 能表达租户资源与优先级，却不自动提供 guest 就绪语义。

E2B 全托管服务把节点池、配额和故障处理藏在服务边界后面。对使用者而言，关键是观察公开限额、创建延迟、错误码和 artifact 行为；不能从 API 兼容或营销数字反推出其内部排队算法。自建 CubeSandbox 获得控制权，也同时承担调度、容量和故障值班。

## 七、企业视角：供给 SLO 应该怎么写

供给 SLO 至少包含四项：

| 指标 | 定义示例 | 不能混淆的量 |
|---|---|---|
| 创建成功率 | 在截止时间内进入 Ready 的请求比例 | 请求接受率、任务完成率 |
| Ready P99 | 从接受到可执行的尾延迟 | 单次冷启动样本 |
| 饱和度 | 节点资源、队列、槽位的水位 | 平均 CPU 利用率 |
| 重试/拒绝率 | 按 reason code 分类 | 模型执行失败 |

监控面板应能沿 `request_id → operation_id → sandbox_id → node_id` 追踪一条请求。安全审计还需要租户、模板 digest、网络策略版本和凭据引用。告警不仅看“创建失败”，还要看排队增长、P99 恶化、孤儿操作和重试风暴。

## 本章小结

万级沙箱不是把单机启动命令复制一万次。请求层用鉴权、限流、队列和背压吸收洪峰；调度层根据资源、模板、网络和故障域选择节点并做可过期预留；执行层在 Cubelet 上受存储、KVM、网络和健康检查槽位保护。到达率、并发数、创建服务率和完成率必须分开测量。60 ms 之类的端到端指标不能被拆成未经 tracing 证明的阶段耗时。下一章继续处理“造得出”之后的问题：多租户公平、弹性伸缩和故障域。

## 思考题（能算账的那种）

1. 到达率为 200/s，节点数 100，每节点创建服务率有 1.5/s、3/s 两种情形。分别计算 60 秒后的队列变化，并加入 10% 重试流量后重新计算。
2. 某节点有存储槽位 8、KVM 槽位 16、网络槽位 20、健康检查槽位 12。计算理论并发创建上限，并列出为什么这个 `min` 仍不是实际服务率。
3. 设计一条从 API 接受请求到 Ready 的 tracing span 树，要求能区分排队、调度、存储、KVM、网络和健康检查，同时说明哪些字段不能写入普通日志。
