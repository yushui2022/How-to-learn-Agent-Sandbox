## 引子：同一个沙箱，两种用法

一位数据分析师在云平台上开了一个 Linux 环境，手动跑 notebook：她上传数据集、装依赖、调试、出图、导出报表，用时半天。同一个环境，第二天被接给了另一个东西——一个数据分析 Agent：用户一句"帮我分析这三个月的流失用户特征，出一份带图表的报告"，它自主决定装什么包、写什么代码、先跑什么后跑什么，30 步之后交出成品。

**环境是同一个，用法是两个物种。**

前者的使用者是人：她会自己装错包、自己发现、自己修——她是环境的所有者，出了问题她负责。后者的使用者是模型：它不会为环境负责，它只负责"下一步生成什么代码"；环境脏了它不知道，密钥被打印进日志它不心疼，第 3 步埋下的污染它会带着跑完 30 步。

这正是很多企业的困惑来源："我们已经有容器平台/虚拟机平台了，为什么还要一个'Agent 沙箱'？"——因为这个问题混淆了两种用法。本章先立一把判别的尺子，再回答企业真正关心的问题：**Agent 沙箱到底能拿来做什么生意，做到什么规模。**

## 一、四问判别：Agent 沙箱 ≠ 通用代码沙箱

"沙箱"这个词太老了，老到在线判题（OJ）、CI 流水线、Replit、浏览器插件都在用。它们是沙箱，但不是 Agent 沙箱。判别只需要四个问题——前两问判"是谁"，后两问判"环境扮演什么角色"：

| 判别问题 | 通用代码沙箱 | Agent 沙箱 |
|---|---|---|
| **① 代码是谁写的？** | 人（用户提交、工程师编写） | **模型现场生成，无人 Review** |
| **② 怎么执行？** | 一次性提交运行，结果交还给人 | **自主循环**：LLM 思考 → 执行 → 读结果 → 再决策 |
| **③ 环境扮演什么角色？** | 隔离边界（防代码伤外面） | **Agent 的"手"和"工作记忆"**（文件系统承载多步状态） |
| **④ 启动速度意味着什么？** | 体验问题（慢一点用户等得起） | **吞吐问题**（速度 × 调用次数，见第一章两笔账） |

拿这四问过一遍常见场景：

- **在线判题（OJ）**：代码是学生写的（①人），一次性运行（②非循环），环境用完即弃（③纯边界），提交频率低（④体验问题）——通用沙箱，Docker 足矣。
- **CI 流水线**：代码是工程师提交并 Review 过的（①人且可信），单次构建（②非循环）——通用沙箱，且信任前提满足容器的契约。
- **Replit/云 IDE**：代码人写（①人），交互式执行（②非自主循环），环境是"工作台"（③人的工作台而非 Agent 的记忆）——通用沙箱的高级形态。
- **ChatGPT Code Interpreter**：代码模型生成（①模型），跑完读输出决定下一句回答（②轻量循环）——**Agent 沙箱**，尽管是最简单的一种。

四问全部命中"右列"，才是 Agent 沙箱。这个判别不是学究气——它直接决定选型：**通用沙箱的评估重点是"隔离一次够不够好"；Agent 沙箱的评估重点是"每秒能供给多少个、状态怎么管、循环怎么闭环"。** 第一章的四大新问题（不可信、联网、状态、规模），本质就是右列四问推导出的工程需求。

## 二、六种用法原型：Agent 沙箱的生意全景

判别清楚了"是什么"，现在回答"用来做什么"。按工作流的复杂度，Agent 沙箱的用法收敛为六种原型——每一种都有代表产品和企业形态。

### 原型一：Code Interpreter——把"能算"嵌进产品

**工作流**：模型生成代码 → 沙箱即时执行 → 结果（数字/图表/文件）回流对话。

这是最简单也最普及的原型。ChatGPT 的 Code Interpreter（2023 年 6 月上线）是教科书案例：用户问"这两个月的数据有什么异常"，模型写一段 Pandas、在沙箱里跑、把图表贴回对话——**整个过程用户没写一行代码**。E2B 的第一批主流客户就是这个场景：给自己的 AI 产品嵌一个安全的代码执行后端。

**企业形态**：产品内嵌的数据问答、计算引擎、报表生成。任何"需要精确计算但不能让用户写代码"的产品功能，都是这个原型的变体。

**对沙箱的要求**：中等——单次执行、短生命周期、结果要能带出（文件/artifact 回传）。安全重点在资源配额与网络出口。

### 原型二：Coding Agent——把"能改"交出去

**工作流**：给定一个代码仓库和任务 → Agent 多步循环（读代码 → 改文件 → 装依赖 → 跑测试 → 修失败 → 再改）→ 产出补丁或 PR。

这是过去两年升温最快的原型。学术侧，SWE-agent（普林斯顿，2024）和 OpenHands（原 OpenDevin）定义了"Agent 修真实 GitHub issue"的范式，SWE-bench（ICLR 2024）成了事实评测标准；产业侧，Devin（Cognition，2024）把"全自主软件工程师"推上舞台，Cursor、Claude Code 则把循环半自动化地嵌进 IDE。

**企业形态**：内部研发提效平台——批量代码迁移、依赖升级、bug 修复流水线、遗留代码重构。

**对沙箱的要求**：高——环境要完整（git、编译器、测试框架）、状态要持续（几十步的文件与依赖累积）、网络要可控（拉包但防注入）。这是"环境即工作记忆"最典型的场景：第 30 步的修复依赖第 3 步 `git checkout` 的状态。

### 原型三：数据分析 Agent——把"能查"自动化

**工作流**：接数据源 → Agent 写分析代码 → 沙箱执行 → 产出图表/报表/结论 → 按需迭代。

与原型一的区别在**深度**：不是一次计算，而是一条多步分析流水线——取数、清洗、建模、可视化、撰写报告。Manus（2025 年爆火的通用 Agent 产品）的分析类任务、各家的 BI Copilot 都是此列。它的企业价值有三个锚点：**结果可复现**（同一问题任何时候重跑结论一致）、**数据不落地**（数据留在平台侧，沙箱只是计算现场）、**过程可审计**（每一步代码都有记录）。

**企业形态**：报表自动化、定期经营分析、风控与合规扫描。

**对沙箱的要求**：高——中等生命周期、大量文件 IO（第一章思考题 2 的负载画像）、凭据管控（连数据源需要密钥，而密钥绝不能进沙箱——第十章的主题在此埋下）。

### 原型四：Computer-use / 工具执行 Agent——把"能操作"授权出去

**工作流**：Agent 以通用命令与浏览器操作为行动空间，在沙箱内完成"打开网页 → 填表 → 下载 → 提交"这类操作流。

Anthropic 的 computer use（2024）与 OpenAI 的 Operator（2025）把这条路推向主流。技术上它往往是"沙箱里再跑一个浏览器/桌面"——沙箱从"代码执行环境"升格为"数字工作台"。

**企业形态**：流程自动化（RPA 的 Agent 化）、跨系统操作、批量信息采集。

**对沙箱的要求**：最高之一——长生命周期、有头浏览器吃资源、网络策略要精细到域名级（允许访问目标网站、拦截其他一切）。

### 原型五：Agent 评测——把"能考"变成基础设施

**工作流**：为评测任务制作标准环境（固定 commit/依赖/数据）→ 从模板批量派生 N 个沙箱 → N 个模型副本并行作答 → 自动判定打分。

SWE-bench 一年多的演化证明：**没有可控的环境供给，就没有可信的评测**。论文里的 500 个 issue，每个都要一个"出生即一致"的环境；模型每次迭代都要全量重跑；环境漂移一分，分数就失真一分。企业侧同理——你的"模型选型"和"回归测试"需要的是同一套东西：千份一模一样的沙箱、按需创建、用完即毁。

**企业形态**：模型评测平台、Agent 上线前的回归测试、A/B 对比基座。

**对沙箱的要求**：极端——爆发式创建（几分钟内数百上千个）、完全一致的初始状态（快照派生）、集中销毁。这是普通业务负载的千倍放大镜，第十七章会专门拆解它的供给曲线。

### 原型六：多 Agent 协作——把"能组队"跑起来

**工作流**：一个 orchestrator Agent 拆解任务 → 分派给多个 worker Agent（各配沙箱）→ 并行执行 → 汇总整合。

复杂任务的并行拆解是单 Agent 循环的自然延伸。LangGraph、MetaGPT 等编排框架提供了拓扑的"语法"，而每个节点真正落地的"物理层"就是沙箱。Manus 类产品的底层，多数是"规划者 + 执行者 + 审查者"各配环境的拓扑。

**企业形态**：复杂任务自动化平台——一份 200 页的报告 = 一个规划沙箱 + N 个检索沙箱 + 一个汇总沙箱。

**对沙箱的要求**：最高——所有前五原型的要求叠加，再乘上拓扑问题：沙箱间怎么通信、状态怎么共享、一个 worker 失控怎么不拖垮全局。这是第二十章的专属领地。

### 六原型速查表

| 原型 | 工作流核心 | 代表 | 对沙箱的最大挑战 |
|---|---|---|---|
| Code Interpreter | 一次执行回对话 | ChatGPT CI、E2B 客户 | 结果回传、资源配额 |
| Coding Agent | 多步改仓库 | SWE-agent、Devin、Cursor | 状态持续、环境完整 |
| 数据分析 Agent | 多步产报表 | Manus、BI Copilot | 数据不落地、凭据管控 |
| Computer-use | 操作流自动化 | Claude computer use、Operator | 长生命周期、域名级网络策略 |
| Agent 评测 | 千份一致并行跑 | SWE-bench 基础设施 | 爆发创建、快照派生 |
| 多 Agent 协作 | 拓扑并行编排 | LangGraph + 沙箱运行时 | 通信、共享状态、失败传播 |

注意一条暗线：**从原型一到原型六，对沙箱的要求单调递增**——生命周期变长、状态变重、并发变多、隔离边界变复杂。企业选型时先问"我落在第几档"，就避免了"用原型一的预算操原型六的心"或反过来。

## 三、并发沙箱能干什么：规模视角的三笔账

第二章讲了"墙的材质"，本章前两节讲了"拿来做什么"。现在把它们合到企业最关心的一个维度上：**规模**。并发能力不是运维指标，它直接定义业务上限——三笔账说明这一点。

**账一：任务视角——一次任务，几十个生命周期。** 一个多步 Agent 任务（原型二～六）意味着几十次工具调用循环。即便采用会话级复用（启动只付一次，第一章的账），一个平台每天 10 万个任务，就是 10 万次创建 + 10 万个并发峰值的供给需求。**沙箱创建的每秒吞吐，就是任务排队的反比例函数。**

**账二：平台视角——晚高峰即容量规划。** 一万个用户同时在线，每人一个会话、每会话一个沙箱：这是"常驻型"账。再叠加原型五的"评测洪峰"（一个团队一次评测就可能占用上千个沙箱），平台的容量规划必须同时算"交互式负载的持续水位"和"批处理负载的脉冲峰值"——这两笔账怎么不打架，是第十九章多租户公平的主题。

**账三：成本视角——从"养机器"到"按需即焚"。** 传统模式养常驻机器，利用率通常在 10%～20%（业界公开数据里，企业服务器平均利用率长期低位徘徊）；Agent 沙箱模式是按需创建、用完即毁——它把成本结构从 CapEx（买机器）变成了近似 Serverless 的 OpEx（用多少算多少）。但这个转换**有前提**：第一章第二笔账已经说过，前提就是毫秒级启动 + MB 级开销——否则"即焚"焚不起。

三笔账合起来，就是本章对企业"并发沙箱能干什么"的回答：**它决定你的任务吞吐上限（账一）、你的服务容量形态（账二）、你的成本结构（账三）。** 而这三笔账的所有前提，最终都落到那两个数字上——60ms 与 5MB。

## 四、风险清单与工程答案

第一章列了四大新问题，这里把它们翻译成企业的风险清单与对应的工程答案——每一条都是后续章节的入口：

| 企业风险 | 场景化描述 | 工程答案 | 详见 |
|---|---|---|---|
| 不可信代码执行 | 模型生成的危险命令/被注入的代码跑在生产基础设施上 | 硬件级隔离 + 网络出口管控 | 第二、七章 |
| secret 泄露 | 模型把 API Key 打进日志/写进代码/被诱导外传 | 凭据不进沙箱，网关侧注入 | 第十章 |
| 环境污染与不可复现 | 任务互相污染、评测环境漂移导致结论失真 | 模板 + 快照派生，一任务一环境 | 第九、十七章 |
| 审计盲区 | 出了事故说不清"Agent 到底执行了什么" | 执行轨迹全记录 | 第十三章 |
| 成本失控 | 万级闲置沙箱烧钱、"即焚"变"常驻" | AutoPause + 生命周期策略 | 第十二、十四章 |
| 供给瓶颈 | 晚高峰排队、评测洪峰拖垮交互业务 | 供给链路分层 + 多租户公平 | 第十八、十九章 |

## 本章小结

| 关键认知 | 一句话 |

| 判别标准 | 四问定 Agent 沙箱：代码谁写、怎么执行、环境什么角色、速度什么含义——OJ/CI/Replit 都是沙箱，但不是 Agent 沙箱 |

## 思考题（能算账的那种）

1. 用四问判别标准检验你公司的三个场景（例如：内部脚本平台、AI 客服、数据分析 Agent），哪几个是真 Agent 沙箱？误判（把通用沙箱当 Agent 沙箱采购，或反之）在你的具体场景里会多花/少花多少钱？
2. 你的业务落在六原型的第几档？按"任务数 × 平均生命周期 × 并发峰值"估算你的平台每天需要多少个沙箱生命周期（创建次数），以及稳态同时存活的沙箱数——这两个数字差多少倍？
3. 账三的转换：按你公司当前服务器利用率（拍一个数）和日均 Agent 任务量，粗算"养常驻机器"与"按需即焚"两种模式的月成本差——在什么任务量级下，即焚模式开始明显占优？
